# Развёртывание на Windows 10

Эта инструкция для сервера под Windows 10 без Docker. Всё работает службами Windows и поднимается само после перезагрузки, без входа пользователя в систему:

```
телефоны и ноутбуки
   │  интернет, порты 80 и 443
   ▼
Caddy (служба KassaProxy): HTTPS, сертификат выпускается сам
   │  127.0.0.1:3000, только внутри этой машины
   ▼
Kassa (служба KassaApp): сервер на Node.js, отдаёт API и сайт
   │  127.0.0.1:5432, только внутри этой машины
   ▼
PostgreSQL 16 (служба postgresql-x64-16)
```

Наружу открыты только порты 80 и 443. Приложение и база слушают только саму машину. У каждой службы своя учётная запись без прав (`NT SERVICE\KassaApp`, `NT SERVICE\KassaProxy`): Caddy, который смотрит в интернет, не может прочитать пароль базы, а приложение не может прочитать ключи сертификата.

> **Что проверено, а что нет.** Проверено на Linux: сборка с нуля, миграции, подготовка базы, копия и восстановление (автоматические тесты на настоящей PostgreSQL), Caddyfile и работа через прокси на настоящем Caddy 2.11.4, решения самих скриптов PowerShell (`server/test/powershell-scripts.test.ts`: скрипты под PowerShell 7 на «выдуманной машине» с настоящим git-репозиторием, заглушками `sc.exe`, `icacls.exe`, `npm` и служб; видно, что скрипт решает, в каком порядке делает и что печатает: обновление, возврат после сбоя, копия, восстановление, команды администратора). Синтаксис и совместимость с Windows PowerShell 5.1 проверяет `lint.ps1`, но не сама 5.1. **Ни разу не запускалось на Windows** то, что есть только в ней: службы (WinSW), учётные записи служб и права (`sc.exe`, `icacls`), правила брандмауэра, Планировщик заданий, `powercfg`, `w32tm`, и поведение самой Windows PowerShell 5.1. Для этого в `.github/workflows/ci.yml` написано задание на `windows-latest`, но когда его проверяли, GitHub не запускал на этом репозитории вообще никакие задания (они заканчивались за три секунды без единого шага: причина не подтверждена, похоже на лимиты или оплату аккаунта, см. вкладку Actions). Пока задание не работает, настоящей проверкой будет первая установка: `verify.ps1` (раздел 4) покажет, что вышло, а текст любой ошибки скрипта нужно прислать разработчику.
>
> Независимая проверка набора нашла в нём ошибки, которых прежние прогоны не видели: команды `kassa.ps1` не доходили до приложения, проверка «приложение отвечает» не умела сообщать о неудаче (обновление с неработающей версией заканчивалось словом «Updated»), копии в `BACKUP_DIR` не закрывались от других пользователей, и другое. Всё исправлено и закреплено тестами, но это показывает, что первая установка на настоящей Windows почти наверняка найдёт ещё что-то.

## Что нужно заранее

- Windows 10 (64 бита), учётная запись администратора. Что с поддержкой Windows 10, см. раздел 11.
- **Постоянный внешний (публичный) IP-адрес сервера.** Его показывает https://2ip.ru, если открыть сайт с самого сервера. Адрес вида `192.168.x.x` или `10.x.x.x` не подходит: это адрес внутри вашей сети, и сертификат для него не выпустить. Если сервер за роутером, пробросьте порты 80 и 443 на сервер и закрепите за ним постоянный внутренний адрес.
- Порты 80 и 443 доступны из интернета: открыты у провайдера или хостера и в роутере. Порт 80 нужен не только для первого сертификата, но и для продления (раз в два месяца).
- Верные дата и время (при неверных часах не выпускается сертификат и ломаются сессии). `power.ps1` включает службу времени.
- Интернет на сервере: установка, GitHub, выпуск сертификата.

## 1. Подготовка, один раз

### 1.1 Установить программы

| Что | Откуда | Заметки |
|---|---|---|
| Node.js 22.12 или новее (LTS) | https://nodejs.org | Установщик MSI, всё по умолчанию: он ставит Node для всех пользователей в `C:\Program Files\nodejs`. Версии из nvm, Volta или scoop лежат в папке пользователя, и служба их не прочитает. После установки откройте новое окно PowerShell. Версия 22.12 именно такая, а не «любая 22»: на более старой `npm ci` без ошибки пропускает часть сборщика сайта, и сборка падает с `Cannot find native binding`. |
| Git for Windows | https://git-scm.com | Всё по умолчанию. |
| PostgreSQL **16.x** | https://www.postgresql.org/download/windows/ | Установщик EDB. В списке есть и более новые версии: берите именно 16, пути и имя службы в скриптах для неё. **Запомните пароль пользователя `postgres`**, порт оставьте 5432, язык (Locale) по умолчанию: базу Kassa скрипт создаёт в кодировке UTF8 в любом случае. Stack Builder не нужен. |

### 1.2 Получить код

Откройте **PowerShell от имени администратора** (правый щелчок по «Пуск», «Windows PowerShell (администратор)»). Не ISE: он принимает любое сообщение программ за ошибку.

```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass -Force   # разрешает запуск скриптов, только в этом окне
git clone https://github.com/SalikhovIbrohim/kassa.git C:\kassa\app
cd C:\kassa\app
```

Git берёт главную ветку репозитория сам. Если репозиторий закрытый, откроется окно входа в GitHub.

**Про имя ветки.** Пока работа не влита в основную ветку, у репозитория на GitHub одна ветка, `claude/pensive-edison-be5dwy`, и ветки `main` нет. Везде ниже, где написано `-Ref main`, подставьте имя главной ветки репозитория так, как она называется на GitHub в день установки.

Строку с `Set-ExecutionPolicy` повторяйте в каждом новом окне PowerShell: она действует только в нём. Все скрипты ниже запускайте в окне администратора: файл настроек с паролем базы читают только администраторы, и в обычном окне Node скажет, что файла «нет».

Сообщения скриптов английские, это нормально. Пароли при вводе не показываются совсем (даже звёздочками).

### 1.3 База, настройки, первая сборка

```powershell
.\deploy\windows\setup.ps1
```

Скрипт делает папки в `C:\kassa` (доступ только системе и администраторам: новая папка в корне диска иначе открыта на изменение всем пользователям компьютера), ставит пакеты (`npm ci`, 2-5 минут: окно не закрывайте), **после этого** спрашивает пароль `postgres`, создаёт в PostgreSQL роль и базу `kassa` (роль без лишних прав, база в UTF8), записывает файл настроек `C:\kassa\config\kassa.env` со случайным паролем базы (читать его могут только администраторы и система) и собирает приложение. Повторный запуск безопасен для данных: что есть, остаётся. Но пока служба `KassaApp` работает, скрипт откажется (он заново ставит пакеты, из которых приложение запущено): для новой версии есть `update.ps1`.

Если `pg_hba.conf` PostgreSQL пускает на вход не только эту машину, скрипт предупредит: оставьте в нём только строки для `127.0.0.1` и `::1` и перезапустите службу PostgreSQL.

В файле настроек уже стоят `NODE_ENV=production` (cookie сессии получают флаг `Secure`), **`TRUST_PROXY=127.0.0.1`** и `HOST=127.0.0.1`. Первая строка про прокси: Caddy стоит на этой же машине и сообщает серверу настоящий адрес клиента. Без неё защита входа от перебора пароля видит всех как один адрес, и один посторонний может заблокировать вход всем, включая владельца. Файл можно править (`notepad C:\kassa\config\kassa.env`, затем `Restart-Service KassaApp`), но эти три строки должны остаться: `install-services.ps1` не продолжит без них.

### 1.4 WinSW и Caddy

```powershell
.\deploy\windows\download-tools.ps1
```

Скачивает WinSW 2.12.0 (оболочка, которая делает из программы службу Windows) и Caddy 2.11.4 (прокси с HTTPS) со страниц их релизов на GitHub в `C:\kassa\tools` и сверяет SHA-256: файл с другим хэшем удаляется, и скрипт останавливается. Версии и хэши записаны в начале скрипта. Хэши посчитаны по файлам этих релизов, и для Caddy результат совпал с контрольной суммой (SHA-512) из списка в самом релизе.

Нет интернета на сервере: скачайте те же два файла на другом компьютере и положите в `C:\kassa\tools` как `WinSW-x64.exe` и `caddy.exe`. Переименовывайте командой `Move-Item`, а не мышью: при скрытых расширениях Проводник может сделать `caddy.exe.exe`.

### 1.5 Не давать серверу уснуть и следить за часами

```powershell
.\deploy\windows\power.ps1
```

Выключает сон и гибернацию при питании от сети (крышка ноутбука при этом тоже ничего не делает) и включает службу времени Windows. Если после отключения электричества машина сама не включается, найдите в BIOS пункт «Restore on AC Power Loss» (или «After power failure») и поставьте «Power On». Бесперебойник (UPS) избавит от обрывов посреди записи.

## 2. Пользователи и начальные остатки

Пользователей и начальные остатки заводит разработчик, интерфейса для этого нет. Скрипт `kassa.ps1` запускает те же команды с настройками этой машины:

```powershell
.\deploy\windows\kassa.ps1 create-user --login ivan --role cashier --name "Иван Петров"
.\deploy\windows\kassa.ps1 create-user --login owner --role viewer --name "Владелец"
.\deploy\windows\kassa.ps1 set-opening-balance --currency RUB --amount 45000.50
.\deploy\windows\kassa.ps1 set-opening-balance --currency USD --amount 300
.\deploy\windows\kassa.ps1 list-users
.\deploy\windows\kassa.ps1 help
```

- **Имена и суммы выдуманные**: подставьте свои. В справке `help` вместо `npm run admin --` читайте `.\deploy\windows\kassa.ps1`.
- Пароль спросят дважды, при вводе он не виден, не короче 8 символов.
- Сумма с **точкой** (`45000.50`): с запятой PowerShell разобьёт её на два аргумента.
- **Начальный остаток задаётся один раз, до первых операций.** Повторная команда заменяет значение и сдвигает все остатки, в том числе за прошлые дни; в историю она не попадает. Скрипт предупредит, если операции уже есть.

## 3. Службы и HTTPS

Адрес. Пока нет своего домена, берём бесплатный адрес на вашем публичном IP: к IP через дефисы добавьте `.sslip.io`. Для `203.0.113.5` это `203-0-113-5.sslip.io`. Он сам указывает на этот IP, сертификат для него бесплатный (Let's Encrypt). С ноутбука `nslookup 203-0-113-5.sslip.io` должен вернуть ваш IP; если нет, имя в вашей сети блокируют, и нужен свой домен (#10).

```powershell
.\deploy\windows\install-services.ps1 -Site 203-0-113-5.sslip.io
```

Скрипт:

- пишет Caddyfile (прежний, если он отличался, сохраняется как `Caddyfile.<дата>.bak`);
- ставит службы `KassaApp` и `KassaProxy` (запуск автоматический, с задержкой после старта Windows, перезапуск при сбое через 10, 30, 60 секунд), каждой своя учётная запись `NT SERVICE\<имя>` и права только на то, что ей нужно;
- открывает порты 80 и 443 в брандмауэре Windows;
- заставляет службу PostgreSQL самой запускаться снова после сбоя;
- запускает всё и проверяет, что приложение отвечает и что прокси слушает 80 и 443.

PostgreSQL уже работает своей службой. Повторный запуск заменяет службы. Если Node.js стоит в папке пользователя или службы не запускаются под своими учётными записями, скрипт остановится на проверке «приложение отвечает» и покажет её результат; причину ищите в `C:\kassa\logs\KassaApp.err.log` (раздел 9). Запасной выход: `-ServiceAccount LocalSystem` (вместе с `-Site`), но тогда службы получают все права системы.

Первый запуск Caddy просит у Let's Encrypt сертификат: это до минуты. Через минуту в `C:\kassa\logs\KassaProxy.err.log` должна быть строка `certificate obtained successfully`:

```powershell
Select-String C:\kassa\logs\KassaProxy.err.log -Pattern 'certificate obtained'
```

**Смена адреса позже** (купили домен, #10): сначала у домена A-запись на IP сервера и проверка `nslookup kassa.example.ru`, и только потом `.\deploy\windows\install-services.ps1 -Site kassa.example.ru` (иначе Caddy за минуты потратит лимит неудачных проверок Let's Encrypt, около пяти в час). Куки и значок «на экране Домой» привязаны к старому адресу: кассирам придётся войти заново и добавить значок заново.

### 3.1 Если порты 80 и 443 на сервере уже заняты

Так бывает на машине, где уже работает другой сайт или прокси (IIS, свой Caddy). Второй Caddy на тех же портах всё сломает, поэтому Касса ставится только как служба `KassaApp` на внутренний порт, а наружу её отдаёт тот прокси, что уже есть.

1. Заранее задайте свободный порт Кассы в файле настроек (`C:\kassa\config\kassa.env`, строка `PORT=`), например `PORT=3200`. Список занятых портов: `netstat -ano | findstr LISTENING`.
2. Вместо обычной установки запустите:
   ```powershell
   .\deploy\windows\install-services.ps1 -Site 94-158-63-17.sslip.io -NoProxy
   ```
   (имя это IP сервера через дефисы и `.sslip.io`, или ваш домен). Скрипт поставит только `KassaApp`, не откроет порты в брандмауэре и в конце напечатает блок для Caddyfile вашего прокси.
3. Добавьте напечатанный блок в конец Caddyfile существующего Caddy, не меняя остальное:
   ```
   94-158-63-17.sslip.io {
       reverse_proxy 127.0.0.1:3200
   }
   ```
   Сначала сохраните копию Caddyfile, потом проверьте и перечитайте без остановки сайта, который там уже работает (путь к `caddy.exe` и Caddyfile свой):
   ```powershell
   Copy-Item <Caddyfile> <Caddyfile>.bak
   <caddy.exe> validate --config <Caddyfile>
   <caddy.exe> reload --config <Caddyfile>
   ```
   Если `validate` ругается, `reload` не делайте: старый конфиг продолжает работать. Если у существующего Caddy порт 80 занят (его держит IIS), сертификат он получит проверкой на порту 443, этого достаточно.
4. Проверка этой установки: `.\deploy\windows\verify.ps1 -Site 94-158-63-17.sslip.io -NoProxy`. Копии базы, обновление и откат работают так же, как в разделах 5 и 6.

### 3.2 Telegram Mini App (по желанию)

Нужно после того, как сайт работает по https. Это шаги для вас, не для сервера:

1. В Telegram откройте `@BotFather`, команда `/newbot`, имя и логин бота (логин оканчивается на `bot`). Он выдаст **токен**: длинная строка с двоеточием. Никому не показывайте и не вставляйте его в чаты и тикеты.
2. Там же: `/mybots`, ваш бот, `Bot Settings`, `Menu Button`, `Configure menu button`: укажите адрес сайта (`https://94-158-63-17.sslip.io`) и подпись кнопки («Касса»). Теперь у бота в чате есть кнопка, которая открывает Кассу внутри Telegram.
3. На сервере добавьте токен в файл настроек и перезапустите службу (PowerShell от администратора):
   ```powershell
   Add-Content C:\kassa\config\kassa.env "TELEGRAM_BOT_TOKEN=ВАШ_ТОКЕН"
   Restart-Service KassaApp
   ```
4. Откройте бота в Telegram, нажмите кнопку, войдите логином и паролем и нажмите «Привязать Telegram». В следующий раз Касса откроется без пароля.

Telegram у ваших людей работает через VPN, поэтому вход по паролю остаётся основным.

### 3.3 Сообщения в группу Telegram (по желанию)

Касса пишет в группу Telegram про приходы от клиентов и про расходы: кто принял или выдал, сколько, по какому курсу, сколько это в долларах, код клиента, получатель, комментарий. Исправление и удаление такой записи тоже приходят сообщением («Было», «Стало»). Про какие категории писать, решает владелец отметкой «Сообщать в группу Telegram» на вкладке «Категории»: сразу отмечены все расходы и «Оплата от клиента», остальные приходы (долг, субаренда, прочее) не отмечены. Нужен тот же бот, что и для Mini App (раздел 3.2, шаги 1 и 3). Сервер должен доставать до `api.telegram.org`: откройте `https://api.telegram.org` в браузере на сервере, должна открыться страница с ошибкой от Telegram, а не «не удаётся открыть».

1. Создайте группу в Telegram (или возьмите существующую) и добавьте в неё бота по имени (`@excoskassabot`). Включить в BotFather ничего не нужно, кроме `Allow Groups` (по умолчанию включено).
2. Если в группе есть темы (разделы), как «Приход» и «Расход», напишите `/start@excoskassabot` **в каждой из нужных тем**. Если тем нет, достаточно одного сообщения в группе.
3. На сервере найдите номера (PowerShell от администратора):
   ```powershell
   .\deploy\windows\kassa.ps1 telegram-chats
   ```
   Номера можно узнать и без бота: в Telegram на компьютере нажмите правой кнопкой на любое сообщение в нужной теме и выберите «Копировать ссылку на сообщение». Ссылка вида `https://t.me/c/1234567890/3/15`: номер группы это `-100` и первое число (`-1001234567890`), номер темы это второе число (`3`). Если в ссылке только два числа, сообщение из главной темы.
   В списке будет строка с названием группы и номером вида `-1001234567890` (минус в начале обязателен), а под ней номера тем, в которых бот видел команду: `topic 3  Приход`, `topic 5  Расход`. Если список пуст или нужной темы нет, повторите шаг 2 и команду: Telegram хранит такие события сутки. Бот видит только команды: надпись «не имеет доступа к сообщениям» у бота в списке участников это нормально, на отправку она не влияет.
4. Впишите номера в файл настроек и перезапустите службу (тему можно не указывать: вид записей без темы идёт в главную тему группы, «General»):
   ```powershell
   Add-Content C:\kassa\config\kassa.env "TELEGRAM_GROUP_CHAT_ID=-1001234567890"
   Add-Content C:\kassa\config\kassa.env "TELEGRAM_THREAD_INCOME=3"
   Add-Content C:\kassa\config\kassa.env "TELEGRAM_THREAD_EXPENSE=5"
   Restart-Service KassaApp
   ```
5. Проверьте: `.\deploy\windows\kassa.ps1 telegram-test`. В каждой теме должно появиться «Касса: проверка связи». Дальше записи приходят сами.

Если Telegram недоступен, запись всё равно сохраняется, а сообщение ждёт в очереди и уходит позже (с растущими паузами, до 15 минут), по порядку. Сообщение, которое Telegram не принимает совсем (бота убрали из группы, неверный номер), после этого пропускается, а причина остаётся в таблице `telegram_outbox`. Что видят в группе все её участники, зависит от того, кого вы туда добавили: коды клиентов и суммы уходят в Telegram.

### 3.4 Запись приходов от клиентов в 1С (по желанию)

Приход с категорией «Оплата от клиента» Касса записывает в 1С (база Cosmo) приходным кассовым ордером «Оплата покупателя» по OData (подробности в README, раздел «Запись в 1С»). **База боевая и копии у неё нет, один документ может стоить больше 10 000 $, поэтому включайте по шагам и не пропускайте первый.**

1. **Сделайте копию информационной базы** (выгрузка `.dt` из конфигуратора) и положите её в безопасное место. Без этого не включайте.
2. Впишите настройки (значения `COSMO_ODATA_*` те же, что в `secrets.env` рядом со скриптами; не показывайте их никому и не вставляйте в чат). Ключи ниже взяты из `HANDOFF-kassa-cosmo.md`: организация, касса «Москва», валюта «Доллар» (860):
   ```powershell
   Add-Content C:\kassa\config\kassa.env "COSMO_1C_MODE=preview"
   Add-Content C:\kassa\config\kassa.env "COSMO_ODATA_URL=<адрес OData базы Cosmo>"
   Add-Content C:\kassa\config\kassa.env "COSMO_ODATA_USER=<логин>"
   Add-Content C:\kassa\config\kassa.env "COSMO_ODATA_PASSWORD=<пароль>"
   Add-Content C:\kassa\config\kassa.env "COSMO_1C_ORGANIZATION_KEY=bf358780-5b3f-11f1-8cb6-b8cb29f61f4c"
   Add-Content C:\kassa\config\kassa.env "COSMO_1C_KASSA_KEY=0d2cb474-924a-11f1-8cb7-b8cb29f61f4c"
   Add-Content C:\kassa\config\kassa.env "COSMO_1C_CURRENCY_KEY=542c581a-49bf-11ef-afed-8c1d965e9add"
   Restart-Service KassaApp
   ```
3. Проверьте связь, это только чтение: `.\deploy\windows\kassa.ps1 onec-check`. Должно быть «Всё готово», касса «Москва», валюта «Доллар». Строки «ПРОБЛЕМА» исправьте до следующего шага.
4. **Репетиция** (`preview`, как выше): внесите приход клиента и посмотрите `.\deploy\windows\kassa.ps1 onec-status`: там написано, какой документ был бы записан (контрагент, договор, сумма в долларах, дата). В 1С ничего не пишется.
5. **Первый боевой приход, одному клиенту.** Замените режим и ограничьте клиентов одним тестовым (коды как `А339`), перезапустите службу. Внесите приход на 0,01 $ (или рубли по курсу, дающие 0,01 $) этому клиенту. Проверьте документ в 1С (контрагент, договор, проводка Дт 5010 / Кт 6310), затем сами пометьте его на удаление в 1С: Касса 1С ничего не удаляет.
6. Уберите `COSMO_1C_CLIENTS`, перезапустите службу: пишутся приходы всех клиентов.

Режим и список клиентов правятся в `kassa.env` (после правки `Restart-Service KassaApp`). Отключить совсем: `COSMO_1C_MODE=off`.

Если приход не записался, в группу Telegram приходит сообщение с причиной. Дальше: `onec-status` (список), `onec-retry --id N` (повторить), `onec-skip --id N` (не записывать). Касса не выбирает контрагента, если их несколько или нет, и не создаёт новых: завести или поправить его нужно в 1С, запись повторится сама.

## 5. Резервные копии

Деньги владельца лежат в одной базе. Без копий потеря диска это потеря денег.

### 5.1 Что делает копия

`deploy\windows\backup.ps1` (внутри `deploy\backup.mjs` и `pg_dump`) делает один сжатый файл `kassa-<дата>-<время>.dump`, читает его обратно и проверяет, что в нём таблица операций, оставляет последние 14 копий и удаляет только более старые копии этой базы (других файлов в папке не трогает). Копия, которую `update.ps1` делает перед обновлением, называется `kassa-<дата>-<время>-before-update.dump` и хранится отдельно: последние 5, и ни она не вытесняет ночные копии, ни ночные её. `-Status` смотрит только на ночные. Копия с датой из будущего (часы компьютера когда-то шли неверно) не считается, не удаляется, и скрипт называет её по имени: удалите её сами, когда посмотрите. При любой неудаче код выхода 1, поэтому Планировщик заданий покажет ошибку. Пароль `postgres` не нужен: копию делает роль самого приложения. Приложение работает во время копии. Что произошло, дописывается в `C:\kassa\logs\backup.log`.

```powershell
.\deploy\windows\backup.ps1                 # одна копия сейчас
.\deploy\windows\backup.ps1 -Status         # свежая ли последняя копия (не старше 26 часов)
```

### 5.2 Куда класть копии

По умолчанию в `C:\kassa\backups`. Это тот же диск, что и база: такая копия не спасёт от поломки диска. **Укажите другой диск** (второй внутренний или USB) строкой в `C:\kassa\config\kassa.env`, без кавычек (если в пути есть знак `#`, то в одинарных кавычках: `BACKUP_DIR='D:\Копии #1'`, иначе всё после `#` считается комментарием, и скрипт откажется работать):

```
BACKUP_DIR=D:\kassa-copies
BACKUP_KEEP=14
```

Папка должна быть полным путём. Задание работает от системной учётной записи, а она не открывает папки на других компьютерах: сетевая папка не подойдёт, нужен диск этого компьютера. Скрипт делает **новую** папку доступной только системе и администраторам (уже существующую не трогает: на диске могут лежать чужие файлы, закройте её сами). На диске не NTFS (флешка FAT или exFAT) прав доступа нет вообще: скрипт напишет предупреждение в окне и в `backup.log` и сделает копию всё равно, такую флешку не оставляйте без присмотра. Путь может быть и кириллическим, если его буквы есть в кодовой странице Windows (в русской Windows это так). Копия содержит все записи и хэши паролей: не отправляйте её по почте и не кладите в общий доступ. Копировать файлы с этого диска на другой сервер или в облако (ежедневный дамп в другое хранилище это отдельный тикет, #9) можно любой программой синхронизации.

### 5.3 Расписание в Планировщике заданий

```powershell
.\deploy\windows\schedule-backup.ps1               # каждый день в 03:00
.\deploy\windows\schedule-backup.ps1 -At 02:30
.\deploy\windows\schedule-backup.ps1 -Remove
```

Делает задание «Kassa backup»: ежедневно запускает `backup.ps1` от системной учётной записи; если компьютер был выключен, копия делается, как только он включится; больше часа задание не живёт; при неудаче три повторные попытки с интервалом десять минут. Задание запускается и при питании от батареи (ноутбук вместо сервера, отключили свет). Проверьте сразу: `Start-ScheduledTask -TaskName "Kassa backup"`, подождите минуту и посмотрите результат именно задания: `(Get-ScheduledTask -TaskName 'Kassa backup' | Get-ScheduledTaskInfo).LastTaskResult` должен быть `0` (`267009` значит «ещё работает», подождите). `backup.ps1 -Status` для этого не годится: он будет зелёным и от копии, сделанной руками.

То же руками: «Планировщик заданий», «Создать задачу». Общие: имя `Kassa backup`, «Выполнять вне зависимости от регистрации пользователя», учётная запись `SYSTEM`, «Выполнить с наивысшими правами». Триггер: ежедневно, 03:00; параметры: «Запускать задачу как можно скорее после пропуска запланированного запуска». Действие: программа `powershell.exe`, аргументы `-NoProfile -ExecutionPolicy Bypass -File "C:\kassa\app\deploy\windows\backup.ps1"`.

### 5.4 Как узнать, что копия не сделалась

Четыре способа, от простого к полному:

- `.\deploy\windows\backup.ps1 -Status`: код 1, если копии нет или она старше 26 часов. Ловит и ошибку, и то, что задание вообще не запускалось (выключен компьютер, задание отключено).
- Планировщик заданий, столбец «Последний результат» у задания `Kassa backup`: `0x0` хорошо, другое плохо.
- `C:\kassa\logs\backup.log`: по строке на каждый запуск, `OK` и файл, либо `FAILED` и причина; `WARNING`, если папку копий не удалось закрыть от других пользователей.
- `verify.ps1` показывает всё это вместе.

Открывайте любой из них раз в неделю, пока не появится автоматическое оповещение.

### 5.5 Попробовать копию и восстановить

Копия, которую не пробовали восстановить, это только надежда. Раз в месяц, и обязательно один раз сразу после настройки (копии лежат в `C:\kassa\backups` или в `BACKUP_DIR`):

```powershell
.\deploy\windows\restore.ps1 -From C:\kassa\backups\kassa-20261001-030000.dump -Check
```

Спросит пароль `postgres` (создать базу не может роль приложения). Восстанавливает копию в пробную базу, пишет, что в ней (пользователи, операции, из них удалённых, строки истории, время последней), и удаляет пробную базу. Ничего рабочего не трогает. Копию, сделанную более старой версией программы, он тоже принимает и говорит, чего в ней ещё нет: так и должно быть при откате. Если проверку прервали (закрыли окно, выключили питание), в PostgreSQL остаётся пробная база `kassa_check_<шесть символов>`: она никому не мешает, удалите её в pgAdmin.

**Заменить рабочую базу копией** (после поломки или порчи данных): та же команда с `-Replace` вместо `-Check`. Без одного из двух скрипт ничего не делает и просит выбрать: замена трогает рабочие данные, и угадывать здесь нельзя.

```powershell
.\deploy\windows\restore.ps1 -From C:\kassa\backups\kassa-20261001-030000.dump -Replace
```

Приложение останавливается, копия восстанавливается в новую базу, и только если всё удалось, она занимает место рабочей (обе замены имён происходят одной операцией: выключение питания посреди неё не оставит сервер без базы). **Прежняя рабочая база не удаляется**: она переименовывается в `kassa_before_restore_<дата>`. Если с восстановленными данными всё хорошо, её можно удалить в pgAdmin (или `DROP DATABASE`). Если что-то не удалось, рабочая база остаётся как была, и приложение запускается снова. **Всё, что внесли после времени копии, в ней отсутствует**, так же как смены паролей и отзывы доступа после этого времени.

**Отменить замену** (вернуть прежнюю базу), если восстановленные данные не те. Остановите приложение (`Stop-Service KassaApp`), закройте pgAdmin и выполните одной строкой, подставив дату из имени сохранённой базы (список баз: `& 'C:\Program Files\PostgreSQL\16\bin\psql.exe' -U postgres -d postgres -c "\l"`):

```powershell
& 'C:\Program Files\PostgreSQL\16\bin\psql.exe' -U postgres -d postgres -c "ALTER DATABASE kassa RENAME TO kassa_not_wanted; ALTER DATABASE kassa_before_restore_20261001_143005 RENAME TO kassa;"
Start-Service KassaApp
```

На новой машине (диск потерян): `setup.ps1`, затем `restore.ps1 -From <копия> -Replace`, затем `download-tools.ps1` и `install-services.ps1`, и снова то, что есть только на старой машине: строка `BACKUP_DIR` (и `BACKUP_KEEP`) в `kassa.env`, `power.ps1` и `schedule-backup.ps1`. Пользователи и остатки уже в базе из копии, заводить их заново не нужно.

## 6. Обновление и откат

Обновление одной командой в окне администратора:

```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass -Force
cd C:\kassa\app
.\deploy\windows\update.ps1
```

Что делает скрипт:

1. Забирает список версий с GitHub, **не останавливая** приложение (нет сети: ничего не изменилось). Если в новой версии изменились пакеты, сначала проверяет, что реестр npm доступен: `npm ci` начинает с удаления установленных пакетов, и без связи с реестром приложение осталось бы без них (нет связи: ничего не изменилось).
2. Если новой версии нет, так и говорит и ничего не останавливает.
3. Останавливает приложение (Caddy продолжает работать: посетитель видит фразу «Касса обновляется…», приложение на телефоне хранит внесённое и отправит позже) и на это время выключает автозапуск службы, чтобы перезагрузка посреди обновления не запустила наполовину собранное.
4. Делает **копию базы** с пометкой `before-update` (с ней можно вернуться: её имя печатается в конце и записывается в `C:\kassa\logs\update.log`; хранятся последние 5, отдельно от ночных).
5. Переключается на новую версию, ставит пакеты, только если они изменились, собирает, применяет миграции базы.
6. Запускает приложение, проверяет, что оно отвечает, и возвращает автозапуск.

**Если на каком-то шаге ошибка** (в том числе новая версия запустилась и не отвечает), скрипт говорит какая, пишет `The update failed` и завершается с кодом 1. Если база не менялась (в том числе когда первая же миграция не применилась: каждая применяется целиком или никак), он сам останавливает службу, возвращает, собирает и запускает ту версию, что работала до этого. Если новая версия уже изменила базу (применилась хотя бы одна миграция), старая версия на ней не запустится (она отказывается, иначе показывала бы неверные остатки), и скрипт печатает, как вернуться с копией, сделанной перед обновлением.

### Откат

На прежнюю версию: та же команда с номером версии (короткий номер коммита или тег; `git log --oneline -10` показывает последние):

```powershell
.\deploy\windows\update.ps1 -Ref 1a2b3c4
```

Если новая версия **не меняла базу**, этого достаточно. Если меняла (в ней была новая миграция), старая версия откажется работать на такой базе, и скрипт вернёт новую. Тогда откат только вместе с базой и с потерей всего внесённого после копии, поэтому сначала подумайте, нельзя ли исправить новую версию и обновиться вперёд. Если решили, **два шага, именно в таком порядке**:

```powershell
.\deploy\windows\restore.ps1 -From <копия до обновления>.dump -Replace -NoStart
.\deploy\windows\update.ps1 -Ref 1a2b3c4
```

Копия до обновления называется `kassa-<дата>-<время>-before-update.dump`, её имя `update.ps1` напечатал и записал в `update.log`. `-NoStart` не даёт приложению запуститься между шагами, и служба при этом перестаёт запускаться вместе с компьютером (перезагрузка между шагами тоже не запустит новую версию на восстановленной базе, она применила бы миграции заново); автозапуск возвращает `update.ps1`. Если после `restore.ps1 -NoStart` вы решили не обновлять, а просто запустить: `Start-Service KassaApp`, затем `sc.exe config KassaApp start= delayed-auto`. Копия, сделанная версией старше нынешней (до последней миграции), восстанавливается нормально: так и работает откат.

После отката проверка `git status` показывает «HEAD detached». Это нормально: обычный `.\deploy\windows\update.ps1` без `-Ref` сам вернётся на ветку и обновит. Если ветка, за которой следует эта копия, удалена (слили и удалили), скрипт так и скажет: один раз `update.ps1 -Ref main`, дальше обычная команда следует за главной веткой.

Скрипт собирает приложение сам, а не вызывает `build.ps1`, потому что при смене версии подменяются и скрипты. `build.ps1` нужен только до установки служб (первый раз): на работающем сервере он отказывается запускаться, потому что `npm ci` заменяет пакеты, которыми пользуется приложение.

## 7. Перезагрузка, питание и обновления Windows

- Служба `KassaApp` ждёт PostgreSQL (зависимость) и запускается автоматически, `KassaProxy` тоже. После перезагрузки ничего делать не нужно, входить в Windows не нужно. Через пару минут `verify.ps1` и страница с телефона.
- Windows может сама перезагрузиться после обновлений. Чтобы это не пришлось на рабочее время, задайте «Период активности» (Параметры, Обновление и безопасность, Центр обновления Windows). В Windows 10 Pro можно точнее: `gpedit.msc`, Конфигурация компьютера, Административные шаблоны, Компоненты Windows, Центр обновления Windows, «Настройка автоматического обновления» (4: загрузка и установка по расписанию, например в 03:00). Названия пунктов зависят от сборки Windows.
- Перезагрузка обрывает работу кассиров на несколько минут. Телефон хранит внесённое без связи и отправит, когда сервер вернётся (README, «Работа без связи»), но только пока приложение открыто.
- Если выключается свет, смотрите про BIOS и бесперебойник в 1.5.

## 8. Где что лежит

| Что | Где |
|---|---|
| Код | `C:\kassa\app` (клон репозитория) |
| Настройки и пароль базы | `C:\kassa\config\kassa.env` (не в репозитории) |
| Caddyfile | `C:\kassa\config\Caddyfile` (и прежние версии `.bak`) |
| Журналы | `C:\kassa\logs\`: `KassaApp.out.log`, `KassaApp.err.log`, `KassaProxy.err.log`, `caddy-access.log` (сами ротируются), `backup.log`, `update.log` |
| Службы | `C:\kassa\services\KassaApp\`, `KassaProxy\` (WinSW и его XML) |
| Программы WinSW и Caddy | `C:\kassa\tools` |
| Сертификаты Caddy и их ключи | `C:\kassa\caddy\data` (доступ только у KassaProxy; стоит включить в копию) |
| Копии базы | `C:\kassa\backups` или `BACKUP_DIR` |
| База | в данных PostgreSQL (`C:\Program Files\PostgreSQL\16\data`) |

Каждый день пригодится:

```powershell
Get-Service KassaApp, KassaProxy                              # работают ли
Restart-Service KassaApp                                      # после правки настроек
Get-Content C:\kassa\logs\KassaApp.out.log -Tail 50 -Wait     # журнал приложения вживую
```

Удалить службы (данные остаются, порты 80 и 443 закрываются): `.\deploy\windows\uninstall-services.ps1`.

## 9. Если что-то не работает

Сначала `.\deploy\windows\verify.ps1`: он часто называет причину.

| Что видите | Что значит и что делать |
|---|---|
| `Run this in a PowerShell window opened with "Run as administrator"` | Окно не от администратора. |
| `running scripts is disabled on this system` (в русской Windows по-русски: «выполнение сценариев отключено в этой системе») | В этом окне не выполнена строка `Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass -Force`. |
| `'node' was not found` или `'git' was not found` | Программа не установлена или окно открыто до установки: откройте новое. |
| `The settings file ... does not exist` | Не выполнен `setup.ps1`. |
| `WinSW was not found` или `Caddy was not found` | Не выполнен `download-tools.ps1` (раздел 1.4). |
| `The application does not answer`, `The new version does not answer` | Приложение не запустилось: `C:\kassa\logs\KassaApp.err.log`. |
| `Say what to do with the copy: -Check ... -Replace ...` | `restore.ps1` без `-Check` или `-Replace` ничего не делает: выберите (раздел 5.5). |
| `The npm registry cannot be reached` | Обновление остановилось до всяких изменений: нет связи с реестром npm. Проверьте интернет и повторите. |
| `The service KassaApp is running, and this script reinstalls the packages` | `setup.ps1` на работающем сервере не нужен; для новой версии `update.ps1`. |
| `BACKUP_DIR has a # in it` | Путь с `#` напишите в одинарных кавычках (раздел 5.2). |
| `The proxy does not listen on both port 80 and port 443` | Порты заняты другой программой (IIS, другой веб-сервер): `Get-NetTCPConnection -LocalPort 80 -State Listen`, затем `Get-Process -Id <номер>`. Журнал `KassaProxy.err.log`. |
| `The service ... is still there (marked for deletion)` | Открыто окно «Службы» (`services.msc`) или Диспетчер задач: закройте и повторите, либо перезагрузите машину. |
| `The database ... stores text as ...` | База не в UTF8: удалите её, если в ней нет нужного, и снова `setup.ps1`. |
| `The database was changed by a newer version of Kassa` | Откат на версию старее базы: раздел 6, «Откат». |
| На сайте 503 и фраза «Касса обновляется или временно недоступна…» не уходит | Приложение не работает (Caddy отвечает за него этой фразой): `Get-Service KassaApp`, `KassaApp.err.log`. |
| Служба `KassaApp` падает с `listen EACCES` | Windows зарезервировала порт 3000 (бывает с Hyper-V, WSL2, Docker): `netsh int ipv4 show excludedportrange protocol=tcp`. Выход: другой порт: замените в `C:\kassa\config\kassa.env` строку `PORT=3000` на `PORT=3001` (если строк `PORT` две, действует последняя, так же и в скриптах) и снова `install-services.ps1` (он берёт порт из настроек и для Caddyfile тоже). |
| `detected dubious ownership in repository` в `update.ps1` | Папку клонировал другой пользователь: `git config --global --add safe.directory C:/kassa/app`. |

Дальше:

- **Служба не запускается.** Журналы `KassaApp.err.log` и `KassaApp.wrapper.log`. Запустите приложение вручную, чтобы увидеть ошибку: `Stop-Service KassaApp`, затем в `C:\kassa\app` `node --env-file=C:\kassa\config\kassa.env server\dist\main.js`. Если вручную работает, а службой нет, возможно, мешают права: переустановите с `-ServiceAccount LocalSystem` и сообщите, что это помогло.
- **Сертификат не выпускается.** Порт 80 или 443 закрыт у провайдера, в роутере или занят другой программой. Смотрите `KassaProxy.err.log`. У Let's Encrypt есть лимиты на частые выпуски (около пяти неудач в час для одного имени, около пяти одинаковых сертификатов в неделю): не стирайте `C:\kassa\caddy\data` без нужды и не запускайте установку в цикле.
- **PostgreSQL виден снаружи.** Не должен. С другого компьютера: `Test-NetConnection 203.0.113.5 -Port 5432` (подставьте IP сервера) должна сообщить, что порт закрыт. Если открыт, найдите правило брандмауэра PostgreSQL (`Get-NetFirewallRule -DisplayName "*postgres*"`) и отключите его: приложению внешний доступ не нужен. `verify.ps1` тоже показывает такие правила.
- **Неверное время.** `w32tm /resync` в PowerShell администратора (если не работает: `.\deploy\windows\power.ps1` включает службу времени).
- **Кассиры не могут войти, хотя пароль верный.** Возможно, защита входа заблокировала логин после пяти ошибок (подождать до 15 минут) или `TRUST_PROXY` потерян (раздел 4.3).

## 10. Безопасность в двух словах

- База и приложение доступны только с этой машины, наружу 80 и 443.
- Службы работают без прав администратора, каждая под своей учётной записью. Роль базы не может ничего, кроме своей базы (но владеет ею, потому что миграции применяются при запуске: кто прочитал `kassa.env`, тот может менять базу напрямую).
- Папка `C:\kassa` доступна только системе и администраторам, пароль базы лежит только в `C:\kassa\config\kassa.env`, прочитать его могут администраторы, система и служба `KassaApp`. В репозитории секретов нет.
- Пароль `postgres` в скрипты не записывается: его спрашивают один раз и не оставляют в окне. Новый пароль роли не попадает и в журнал PostgreSQL.
- Заголовки ответа (`X-Content-Type-Options`, `Referrer-Policy`) ставит Caddy. `Strict-Transport-Security` не стоит на бесплатном адресе намеренно (сертификат, который не продлился, иначе запер бы всех без обхода предупреждения): добавьте его в `Caddyfile` после того, как сертификат на настоящем домене успешно продлится.
- Копии базы содержат все записи и хэши паролей: храните их так же бережно, как саму базу.

## 11. Что поддерживать

- **Windows 10.** По имеющимся данным (сроки проверьте у Microsoft), обычная поддержка Windows 10 закончилась 14 октября 2025, дальше обновления безопасности выходят только по платной программе расширенных обновлений (ESU) на ограниченный срок. Сервер в интернете с деньгами владельца стоит перевести на поддерживаемую систему или подключить ESU: это решение владельца (#5). Приложение его не блокирует.
- **Node.js, PostgreSQL 16, Caddy, WinSW.** Сами по себе не обновляются. Раз в месяц смотрите выпуски: обновление Node.js (LTS) и PostgreSQL 16.x ставится обычным установщиком (службы перезапустятся), Caddy и WinSW меняются в `download-tools.ps1` (версия и хэш) и `install-services.ps1` заново. После любого обновления `verify.ps1`.
- **Копии.** Раз в месяц `restore.ps1 -Check` на свежей копии, раз в неделю взгляд на `backup.ps1 -Status`.
