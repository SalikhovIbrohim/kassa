# Касса

Учёт наличных (кассовая книга) для небольшой грузоперевозочной фирмы: кассиры записывают приход и расход в одну общую книгу (смен нет, день сам меняется в 03:00 по Москве), один из них, админ, сверяет кассу с пересчитанными наличными, владелец только смотрит. Сайт (PWA) для iPhone и ноутбука, позже Telegram. Подробности в спеке: issue #1.

## Состав

- `server/`: сервер на Node.js и TypeScript (Fastify), база PostgreSQL. Отдаёт API (`/api/...`) и собранное веб-приложение.
- `web/`: PWA-оболочка на React и TypeScript (Vite).

## Оформление

Экраны сделаны на Tailwind CSS 4 и компонентах в стиле [shadcn/ui](https://ui.shadcn.com/) (`web/src/components/ui`: `button`, `badge`, `card`, `tabs`, `segmented`, `input`, `label`, `select`, `checkbox`, `alert`, `dialog`, `toast`), в стиле прототипа `design/kassa.html` (чёрно-белое «стекло» на сером градиенте, светлая и тёмная тема). Как это устроено:

- **Тема.** Цвета в `web/src/index.css`: названия токенов shadcn (`--background`, `--card`, `--primary`, `--foreground`, `--muted-foreground`, `--border`, `--destructive`, `--radius`) и свои (`--success`, `--warning`, их фоны `-bg`, тени, стекло панелей). Тёмная тема это класс `.dark` на `<html>` (и вариант `dark:` Tailwind). Его ставит `web/src/theme.ts`: выбор «Авто / Светлая / Тёмная» в «Настройках», хранится на устройстве (`localStorage` `kassa.theme`), «Авто» следует системе. Смысл цветов: приход и «сошлось» зелёные (`success`), расход и недостача красные (`destructive`), излишек и «не отправлено» янтарные (`warning`).
- **Компоненты** (`web/src/components/ui`) в форме прототипа: кнопки-капсулы (главная 48 px, `size="lg"` 52 px), вкладки-сегменты, поля и выпадающие списки 50 px на сером стекле с видимой рамкой (`--input-edge`), окно `Dialog` (на телефоне шторка снизу, на компьютере окно по центру, `side="left"` у окна слева), уведомление `toast()` (тёмная капсула сверху, `<Toaster />` в `main.tsx`). Утилиты Tailwind `glass-card`, `glass-bar`, `glass-sheet` (`@utility` в `index.css`).

- **Каркас** (`web/src/Shell.tsx`, разделы в `web/src/sections.tsx`). Разделы зависят от роли: кассир «Приход», «Расход», «Журнал», «Настройки»; главный кассир ещё «Сверка»; админ «Приход», «Расход», «Журнал», «Итоги», «Сверки», «Клиенты», «Категории», «Люди», «Настройки»; владелец «Журнал», «Итоги», «Сверки», «Клиенты», «Настройки». Где компания ведёт рейсы (см. «Сборные грузы»), у админа и владельца есть ещё «Сборные грузы», а у завсклада только «Сборные грузы» и «Настройки». На компьютере (от 960 px) слева меню из стекла по группам (Касса, разделы, Справочники, Настройки), внизу имя и роль; в шапке название раздела и «Выйти». На телефоне внизу капсула из стекла с пятью кнопками и «линзой» под выбранной: четыре выбирает сам человек («Настройки» → «Настроить нижнюю панель», хранится на устройстве, `localStorage` `kassa.tabs.<роль>`), пятая всегда «Настройки», откуда открываются все остальные разделы (со ссылкой «‹ Настройки» назад). Пока на телефоне открыта клавиатура (поле ввода в фокусе и экран стал ниже), панель уезжает вниз, чтобы не закрывать поле и кнопку под ним, и возвращается, когда клавиатура закрыта. В «Настройках» профиль, тема, касса, привязка Telegram и «Выйти». Разделы, открытые раз, остаются живыми: фильтры журнала и период итогов сохраняются.
- **Telegram** (`web/src/telegram.ts`). Внутри Telegram подгружается официальный `telegram-web-app.js`: на телефоне приложение просит весь экран (Fullscreen, Bot API 8.0), отступы берёт из `safeAreaInset` и `contentSafeAreaInset` (переменные `--tg-*`, из них `--app-safe-top` и `--app-safe-bottom`), название раздела стоит в ряду кнопок Telegram, назад ведёт кнопка «Назад» самого Telegram, свайп вниз не закрывает приложение, цвет шапки и фона следуют теме, а пока на телефоне ждут неотправленные записи, Telegram спрашивает перед закрытием. Без скрипта (нет связи с telegram.org) приложение работает с обычной шапкой Telegram.
- **Формы** без большого заголовка, остаток кассы в полосе над формой (у человека «Везде» там же выбор кассы), после записи уведомление «Записано».
- `web/src/index.css`: слои `theme, base, screens, components, utilities`, reset Tailwind (preflight), цвета (переменные `--primary`, `--background` и так далее, одно место) и `screens.css`. В `screens.css` то, что особенное у экранов: журнал, который на телефоне карточки, а на ноутбуке таблица, итоги, список записей, ждущих на телефоне. Этот слой ниже утилит Tailwind, поэтому класс, данный элементу, всегда сильнее.
- Размеры под телефон: кнопки и поля высотой 40 до 48 пикселей, текст в полях 16 пикселей (меньше нельзя: iPhone увеличивает страницу при вводе). Выпадающие списки рисует сама страница (`components/ui/select.tsx`, Radix Select в стиле shadcn): список открывается под полем и не бывает выше половины экрана. Код клиента подсказывает клиентов своим списком под полем; на телефоне поле поднимается наверх, чтобы клавиатура не закрыла подсказки. Валюта это две большие кнопки, под которыми обычные переключатели (radio).
- Компоненты написаны руками по образцу shadcn: реестр `ui.shadcn.com` с сервера, где ведётся работа, не открывается. Где он открывается, новый компонент добавляется командой `npx shadcn@latest add <имя>` из папки `web` (настройки в `web/components.json`), после чего его размеры и цвета подгоняются под эти.
- Псевдоним `@/` указывает на `web/src`. Вкладки это настоящие `role="tab"` (в тестах браузера `getByRole("tab", ...)`).

## Что нужно

- Node.js 22.12 или новее и npm.
- PostgreSQL 16 (локально или в контейнере).

## Запуск для разработки

```sh
npm install
cp .env.example .env        # затем поправьте DATABASE_URL под свою базу
```

Сервер читает настройки из переменных окружения (см. `.env.example`). Например:

```sh
DATABASE_URL=postgres://kassa:kassa@localhost:5432/kassa npm run dev:server   # API на :3000
npm run dev:web                                                               # веб на :5173, /api идёт на :3000
```

Проверка работоспособности: `GET /api/health` отвечает `200` и `{"status":"ok","database":"up"}`, а если база недоступна, `503`.

## Пользователи и вход

Входят логином и паролем. Пользователей ведёт админ на экране, в разделе «Люди» (см. ниже), а первого админа и запасной путь дают команды администратора на сервере. Роли: `cashier` (кассир), `head_cashier` (главный кассир: всё, что кассир, плюс кнопка «Сверить кассу», см. «День кассы и сверка»; сверяет кассу только он), `admin` (админ: стоит выше владельца, вносит записи как кассир, видит и решает всё, что владелец: итоги, историю правок, удалённые записи, списки категорий, и ведёт пользователей; кассу не сверяет) и `viewer` (смотрящий, владелец, только читает). Где компания ведёт рейсы, есть пятая роль, `warehouse` (завсклад: вносит грузы в рейсы, кассу не видит, см. «Сборные грузы»). Каркас один для всех (`web/src/Shell.tsx`), разделы по ролям в `web/src/sections.tsx` (см. «Оформление»). Порядок полей в обеих формах: сначала тип платежа («Откуда деньги» или «На что ушли деньги»), за ним поля, которые он требует (код клиента, номер рейса, контрагент, сотрудник), потом валюта, сумма, курс и комментарий. В формах прихода и расхода названия полей стоят внутри самих полей (сумма, курс, код клиента, номер рейса, контрагент, сотрудник, комментарий), для экранного диктора они остаются подписями; «Откуда деньги» и «На что ушли деньги» остаются заголовком над списком, потому что в списке всегда выбрано значение и подсказке негде стоять. В окне правки записи подписи остаются над полями. Разделы, открытые раз, остаются живыми: фильтры журнала и период итогов сохраняются.

```sh
npm run build                                   # один раз, команды берутся из server/dist
export DATABASE_URL=postgres://...              # в PowerShell: $env:DATABASE_URL = "postgres://..."

npm run admin -w server -- create-user --login ivan --role cashier --name "Иван Петров"
npm run admin -w server -- create-user --login anvar --role admin --name "Анвар"
npm run admin -w server -- create-user --login owner --role viewer
npm run admin -w server -- list-users
npm run admin -w server -- set-role --login ivan --role head_cashier   # меняет роль (cashier, head_cashier, admin, viewer); действует со следующего запроса, записи остаются
npm run admin -w server -- revoke-user --login ivan      # закрывает доступ и все сессии
npm run admin -w server -- restore-user --login ivan     # возвращает доступ, входить нужно заново
npm run admin -w server -- reset-password --login ivan   # новый пароль, все сессии закрываются
npm run admin -w server -- set-opening-balance --currency RUB --amount 12345.67   # начальный остаток
npm run admin -w server -- balances                      # остатки по валютам: начальный + приходы - расходы + разницы сверок
```

**Вкладка «Люди» (только у админа).** Устроена так же, как «Категории»: кнопка «+ Новый» рядом с «Обновить» открывает окно (имя, логин, пароль, роль), а карандаш у человека открывает всё о нём в одном месте: имя, логин, роль, новый пароль (пусто: не менять), и там же «Отключить» или «Включить» и «Удалить» (с подтверждением). Новый пароль и отключение сразу закрывают все сессии человека; новая роль действует с его следующего запроса. Удалить можно только того, кто ничего не вносил, не правил и не сверял: журнал хранит, кто что сделал, поэтому такого человека можно только отключить. Себя админ не может отключить, удалить или лишить роли админа, так что касса не останется без админа. API: `GET /api/admin/users`, `POST /api/admin/users` (`login`, `displayName?`, `password`, `role`), `PATCH /api/admin/users/:id` (любые из `login`, `displayName`, `role`, `password`, `active`), `DELETE /api/admin/users/:id`; ошибки `400` (`bad_login`, `bad_password`, `bad_name`), `409` (`login_taken`, `self`, `has_entries`), `404`, остальным ролям `403`.

Пароль не передаётся в командной строке: его спросят в терминале (символы не показываются) или возьмут из переменной `KASSA_PASSWORD`. Минимум 8 символов. Логин не зависит от регистра букв. На разработке без сборки можно `npm run admin:dev -w server -- ...`.

Как это устроено:

- `POST /api/login` (`login`, `password`) выдаёт сессию в cookie `kassa_session` (HttpOnly, SameSite=Lax, `Secure` на HTTPS). `GET /api/me` говорит, кто вошёл, или отвечает `401`. `POST /api/logout` закрывает сессию этого устройства.
- Сессия живёт 90 дней без использования и продлевается, пока человек пользуется приложением (`SESSION_DAYS`). Пароль нужен при первом входе и по истечении срока.
- Пароли хранятся только хешем (scrypt), в базе лежит хеш токена сессии, а не сам токен.
- Защита от подбора пароля. После 5 неверных паролей подряд для логина вход откладывается: ответ `429` с `Retry-After` и `{ error: "too_many_attempts", retryAfterSeconds }`, ожидание растёт 30 с, 1 мин, 2 мин, 4 мин и так до 15 минут. Попытки во время ожидания отклоняются сразу и ожидание не увеличивают. Верный пароль обнуляет счётчик, через 30 минут без попыток счётчик забывается сам. Несуществующий логин ограничивается так же, по ответам отличить его нельзя. Уже выданные сессии не затрагиваются. Отдельный, более мягкий счётчик (20 неудач) ведётся по адресу клиента: он останавливает перебор многих логинов с одного адреса. Успешный вход его не обнуляет.
- Счётчики хранятся в памяти сервера: после перезапуска службы они пусты. Посторонний может раз в интервал отправить одну неверную попытку на логин кассира и удерживать ему ожидание, до 15 минут: это цена решения «задержка, а не блокировка».
- **За обратным прокси (Caddy) обязательно задайте `TRUST_PROXY`**, например `TRUST_PROXY=127.0.0.1`: только тогда адрес клиента берётся из `X-Forwarded-For`. Без этой настройки заголовок игнорируется (его может подделать любой), и все клиенты за прокси выглядят одним адресом. Тогда один посторонний за 20 неверных попыток выставит ожидание для всех входов, включая владельца. Если сервер видит `X-Forwarded-For` на локальном соединении без `TRUST_PROXY`, он один раз пишет предупреждение в журнал.
- Счётчик логина привязан к учётной записи, а не к написанию: «Ivan», «ivan » и «İvan» (если база читает их как один логин) делят один счётчик.
- Одновременно выполняется не больше 4 проверок пароля (каждая около 100 мс и 32 МБ памяти) и ещё 16 ждут очереди; остальные получают `503` с `Retry-After: 2`, сервер не падает и память не растёт.
- Миграции базы (`server/migrations/*.sql`) применяются при старте сервера и перед командами администратора.
- Для кода следующих тикетов: хуки `app.authenticate` (только вошедшие, кладёт пользователя в `request.user`) и `app.requireRole("cashier", "admin")` ставятся в `onRequest` маршрута: права проверяются раньше, чем тело запроса.

## Приход, расход и остатки

Деньги хранятся целым числом минимальных единиц (копейки, центы), валюты RUB и USD ведутся отдельно, без пересчёта.

- `POST /api/operations` (кассир или админ). Приход: `{ id, type: "income", amountMinor, currency, rateE4?, category?, clientCode?, comment? }`. Расход: `{ id, type: "expense", amountMinor, currency, rateE4?, category, recipient?, clientCode?, comment? }`; `rateE4` это курс (рублей за 1 доллар), умноженный на 10 000 (79,5 это `795000`), от 1 до 1000: у прихода в рублях обязателен, у расхода в рублях необязателен, у долларов запрещён (`400`), см. «Курс и доллары»; `category` это код категории из списков владельца (см. «Категории»): у расхода обязательна, у прихода без неё запись считается оплатой от клиента (`client_payment`, так пишут телефоны, обновлённые не до конца); `clientCode` обязателен, если у категории отмечено «нужен код клиента» (оплата от клиента, возврат клиенту), и запрещён у остальных (`400`). Поле `shiftId` прежних телефонов принимается и игнорируется (смен больше нет, см. «День кассы и сверка»). `id` (uuid в обычной записи 8-4-4-4-12, регистр любой) создаёт клиент: повторная отправка той же операции отвечает `200` и не создаёт дубль, тот же `id` с другим содержимым или от другого кассира даёт `409`. Ответ: сама операция и текущие остатки. Остаток не ограничивает расход: касса ведётся параллельно с таблицей без ограничений, и расход больше остатка записывается, остаток тогда показывается ниже нуля (красным). Отказа «не хватает денег» нет ни при внесении, ни при правке и удалении. Повтор уже принятого расхода отвечает `200`.
- `GET /api/categories` (любой вошедший): `{ categories, income, all }`. `categories` это действующие категории расхода (ответ, который знают прежние телефоны), `income` действующие категории прихода, `all` все категории обоих видов, в том числе архивные (журнал должен называть и их). У каждой: `code`, `kind`, `label`, `sortOrder`, `archived`, `requiresClient`, `countsAsCost`. См. «Категории».
- `GET /api/balances`: остаток по каждой валюте (начальный остаток + приходы - расходы + разницы, найденные при сверках кассы, см. «День кассы и сверка»), доступен любому вошедшему.

## Категории

Категории прихода и расхода лежат в таблице `categories`, а не в коде, и ими управляет админ со своего экрана: раздел «Категории». Владелец (смотрящий) категорий не видит и не меняет. Кассир в формах выбирает категорию из выпадающего списка.

- **Код и подпись.** Операция хранит `code` категории; он выдаётся один раз и не переиспользуется. Подпись админ может переписать, старые записи тогда читаются с новой подписью.
- **Что можно:** добавить категорию (в конец её списка), переименовать, отметить «нужен код клиента» (и рейс, контрагента, сотрудника), двигать вверх и вниз, убрать в архив и вернуть. Удалить нельзя: старые записи её помнят. Архивная категория не предлагается в новых записях, но остаётся в журнале, в итогах (пока в ней что-то есть за период) и в правке той записи, у которой она уже стоит. Последнюю действующую категорию списка в архив убрать нельзя (`409 last_category`). Одинаковые названия в одном списке (без учёта регистра) не принимаются (`409 category_exists`).
- **API админа (только `admin`, остальным `403`):** `POST /api/admin/categories` с `{ kind: "income"|"expense", label, requiresClient? }` и `PATCH /api/admin/categories/:code` с любым из `label`, `requiresClient`, `archived`, `move: "up"|"down"`. Ответ: `{ category, all }`.
- **Порядок категорий.** Кнопки ↑↓ (`move: "up"|"down"`) и перетаскивание строки мышкой на ноутбуке за значок ⠿ (`position`: место в списке своего вида, с 0; дальше конца значит в конец). На телефоне перетаскивания нет, там стрелки.
- **Признак «нужен код клиента»** у категории решает, спрашивает ли форма код клиента: у «Оплата от клиента» и «Возврат клиенту» он есть, у остальных его нет, и сервер его в них не принимает. Признак «не затрата бизнеса» (`countsAsCost`) есть только у «Передача владельцу»: она вычитается из остатка, но в итогах стоит отдельной строкой, а не в расходе. Его админ не меняет.
- **Признаки «нужен номер рейса» и «нужен контрагент»** (`requiresTrip`, `requiresCounterparty`) админ ставит галочками у категории. Тогда форма спрашивает номер рейса (целое число больше нуля, `tripNumber`) и контрагента (текст до 100 символов, `counterparty`), и запись без них не сохраняется: сервер отвечает `400`, а у категорий без галочки эти поля не принимает. Рейс и контрагент видны в журнале, в истории правок и в сообщении в группу. Сразу ни у одной категории галочек нет.
- **Признак «нужен сотрудник»** (`requiresEmployee`) устроен так же: форма спрашивает сотрудника (текст до 100 символов, `employee`), без него запись не сохраняется, у категорий без галочки поле не принимается. Сотрудник виден в журнале, в истории правок и в сообщении в группу.
- **Поля формы расхода.** Поля «Кому выдали» в форме больше нет: кому ушли деньги, говорят «Контрагент» и «Сотрудник», а они появляются только у категорий с такой галочкой. API по-прежнему принимает `recipient` (старые телефоны и записи), правка старой записи сохраняет то, что в ней было.
- **Как добавить категорию.** Кнопка «+ Новая» рядом с «Обновить» открывает окно: приход или расход, название и галочки; новая категория встаёт в конец своего списка.
- **Как устроен экран.** Все категории в одной таблице: сначала приходы (строки чуть зеленоватые), потом расходы (чуть розоватые). В строке тип (Приход / Расход) и галочки: код клиента, рейс, контрагент, сотрудник, в группу Telegram; галочка и тип сохраняются сразу. Тип меняется только у категории, по которой ещё нет записей (`409 category_used`), у «Оплата от клиента» и «Передача владельцу» никогда (`409 kind_locked`); категория другого типа встаёт в конец своего списка (`PATCH /api/admin/categories/:code` с `kind`). Порядок внутри типа: перетаскивание мышкой за ⠿ (стрелок больше нет). После типа колонка «Город» (Везде, Андижан, Москва; поле `city`: `andijan`, `moscow` или `null`): это пометка для отчётов и для 1С, и по ней же формы прихода и расхода прячут чужое: такой же город есть у человека во вкладке «Люди» (`city` в `/api/admin/users`), и человеку Москвы списки «Откуда деньги» и «На что ушли деньги» показывают только московские категории и категории «Везде» (андижанскому наоборот), а человеку без города все. Категория другого города только скрыта, запись с ней сервер не отклоняет: запись, ждущая на телефоне без связи, не должна упасть оттого, что город поменяли. В журнале и в окне правки старая запись по-прежнему видит свою категорию. В `/api/categories` у каждой категории в `all` поле `offered` (показывать ли её этому человеку), а списки `categories` и `income` уже без чужих. Карандаш открывает название и «В архив» (или «Вернуть из архива»).
- **Первые списки.** Расход: шесть прежних категорий (их коды уже стоят в записях) и ещё девятнадцать из таблицы владельца (оплата фура, таможня, обеды, квартира, офис, склад и другие). Приход: оплата от клиента, взяли долг, приход от субаренды, сотрудник вернул долг, прочее. Это предложение для начала: владелец правит списки сам.
- **Записи без категории.** Приходы, внесённые до категорий, хранятся без неё и читаются как «Приход» (оплата клиента).
- **Телефон без связи.** Последние списки копируются в память телефона. Если списков нет совсем, приход всё равно можно внести (как оплату клиента); расход без списка внести нельзя.
- **Итоги:** `expenseByCategory` теперь перечисляет все действующие категории затрат (с нулями) и архивные, у которых за период что-то есть.

## Клиенты

**Справочник клиентов** (миграция 0021, таблица `clients`). У каждого клиента свой код (А707, А34-2), имена могут повторяться. Код пишется одним образом, как его ни набрали: «a707», «А-707», «а707» и просто «707» это «А707» (кириллическая А, цифры как есть; букву можно не набирать). Клиента не удаляют, а отключают: старые записи продолжают его называть.

- **Где.** Раздел «Клиенты» (в меню в группе «Справочники»): поиск по коду, имени и телефону, «+ Новый», карандаш ✎ открывает имя, телефон, заметку и «Отключить». Видят админ и владелец; меняет админ.
- **Загрузить список.** Админ нажимает «Загрузить список» и выбирает файл CSV: в строке код, имя, телефон (через запятую или точку с запятой, первая строка с названиями колонок пропускается; код и имя обязательны). Новые коды добавляются, коды, которые уже есть, остаются как были. Если в файле один код встречается дважды, не загружается ничего, а экран называет код и строки (`POST /api/admin/clients/import`, `400 repeated_codes`).
- **В приходе.** Поле «Код клиента» подсказывает клиентов справочника («А70» → «А707 Карим»). Запись сохраняется с кодом и именем из справочника; кода нет в справочнике: `400 unknown_client` и «Такого клиента нет в справочнике». Пока справочник пуст, принимается любой код, как раньше. Правка старой записи может оставить её прежний код, даже если его нет в справочнике, но поставить новый можно только из справочника.
- **Новый клиент** заводит только админ в разделе «Клиенты» («+ Новый»). В форме прихода и в строке груза кнопки добавления нет: там клиента только выбирают из справочника (набирают код или имя, список подсказывает), а клиента, которого в справочнике нет, сначала заводят в «Клиентах».
- **У клиента обязательно и код, и имя.** Без имени клиент не заводится ни в окне «+ Новый» (`400 bad_name`), ни файлом: список, в котором у строки есть код и нет имени, не загружается совсем, а экран называет такие коды (`400 nameless`). Имя можно поменять, убрать нельзя. Клиенты, заведённые раньше без имени, остаются как были.
- **API.** `GET /api/clients?q=&limit=&all=1` (все, кто вошёл; сначала точный код, потом начало кода, потом имя), `POST /api/admin/clients` (админ; `409 client_exists`, `400 bad_code`), `PATCH /api/admin/clients/:code` (админ: имя, телефон, заметка, `active`).

## Сборные грузы

Раздел для компании, которая возит сборные грузы: рейс это фура, которая идёт от склада к складу и берёт грузы многих клиентов. Раздел живёт в той же базе, что и касса, на том же справочнике клиентов, поэтому **долг клиента один**: его показывают и рейсы, и касса, и считается он каждый раз заново из рейсов и из журнала кассы, нигде не хранится. Код: `server/src/trips.ts` (рейсы и накладные), `server/src/client-debts.ts` (долг), `server/src/warehouses.ts` (склады), миграция `0025_trips.sql`; на экране `web/src/Trips.tsx`, `CargoForm.tsx`, `cargo.ts`.

- **Включается настройкой** `WAREHOUSES`: склады погрузки по порядку через запятую, например `WAREHOUSES=andijan,kokand,tashkent`. Имена `andijan`, `kokand`, `tashkent`, `moscow` код знает сам, другой город пишется с названием (`fergana=Фергана`). Без этой строки раздела нет, роли «Завсклад» нет, у клиента нет ни цены, ни долга, и всё остальное работает как раньше (экраны берут склады с сервера, `GET /api/warehouses`).
- **Рейс.** Номер (один рейс на номер; по нему же расход кассы называет свой рейс), направление («АНДИЖОН - МОСКВА (через КЗХ)»), дата погрузки и дата выезда (это две разные даты: фура выезжает через день-два после погрузки), водитель, телефон, госномера, заметка. Статусы по одному шагу: «Грузится» → «В пути» («Фура выехала», дата выезда ставится сегодняшняя, если её не было) → «Прибыл» («Рейс прибыл», с датой прибытия; она не раньше даты выезда).
- **Строка накладной** повторяет накладную компании в Excel, колонка в колонку: место в фуре («Голова» это передняя часть фуры, «Прицеп» задняя; номер строки на своей части Касса считает сама, как в накладной: «Голова 3», а у груза другого склада счёт свой: «Коканд · Голова 1»), дата приёма груза, получатель (имя: чаще всего сам клиент, иногда другой человек под кодом клиента), код клиента (из справочника: это тот, кому начисляется долг), телефон, бренд, наименование, размер, места, в мешке, вид упаковки (пэ меш, пп меш, коробка, рулон или своё), кол-во штук (если не введено, места × в мешке), общий вес в кг, цена за кг, отправитель (просто имя). Цена подставляется из карточки клиента, получатель из его имени; в строке и то и другое можно поменять. У клиента без своей цены строка должна её назвать (`400 price_required`). Вес хранится в граммах, цена в тысячных доллара, сумма строки это их произведение, без дробных чисел. В «Итоге фуры» места по голове и по прицепу, как в подвале накладной.
- **Долг клиента** = начальный долг + грузы клиента в **прибывших** рейсах − его оплаты в кассе. Оплата это любая неудалённая запись кассы с кодом этого клиента: приход уменьшает долг, расход с кодом клиента («Возврат клиенту») увеличивает. Рубли считаются по курсу записи, как в журнале. Больше нуля: клиент должен; меньше: предоплата. Пока рейс не прибыл, его грузы в долг не входят; вернули рейс «в путь», долг по нему снят.
- **История из картотеки.** Компания, которая до Кассы вела рейсы и оплаты в картотеке Excel, переносит её целиком командой `import-history --file history.json`: клиенты с долгом на начало, рейсы прошлого (у такого рейса нет накладной, только сумма каждого клиента, таблица `trip_sums`; на экране он помечен «Рейс из картотеки», строки груза в него не вносятся), оплаты прошлого по дням с городом (таблица `past_payments`) и накладные рейсов, которые ещё в пути (обычные рейсы со всеми строками). **Оплаты прошлого это не записи кассы:** их нет ни в журнале, ни в остатках касс, они только считаются в долге клиента. Файл загружается целиком или никак; повторная загрузка (картотеку поправили) заменяет загруженную историю и не трогает то, что внесено в Кассе после. В конце команда печатает долги по месяцам рядом с листом «Контроль» картотеки. Файл `history.json` делает из картотеки и накладных скрипт `tools/express/card_file_to_history.py` (см. `tools/express/README.md`). Миграция `0026_waybills_and_history.sql`.
- **Карточка клиента** («Клиенты» → «Карточка», видят админ и владелец): долг на начало, каждый прибывший рейс и каждая оплата по датам (оплата с кассой, которая её приняла; возврат клиенту отдельной строкой) и долг после каждой строки. Это строка картотеки, прочитанная сверху вниз. `GET /api/clients/:code/statement`.
- **Контроль по месяцам** (там же, «Клиенты»): остаток на начало месяца, начислено (рейсы, прибывшие в этом месяце), оплачено, остаток на конец, по всем клиентам вместе, как лист «Контроль» картотеки. `GET /api/debts/control?year=2026`.
- **Округление.** Сумма, которую клиент должен за рейс, это сумма всех его строк в рейсе, округлённая до цента один раз (как в картотеке): строки 389,775 и 796,275 на экране читаются 389,78 и 796,28, а клиент должен 1 186,05.
- **Где виден долг.** В рейсе в «Итогах по клиентам» (колонка «Сейчас должен»), в разделе «Клиенты» у каждого клиента, с итогом «Должны всего» и кнопкой «Только должники», и в кассе под полем «Код клиента» в формах прихода и расхода: кассир видит долг до того, как принял деньги. `GET /api/clients` отдаёт у клиента `priceMilli`, `openingDebtMinor`, `chargedMinor`, `paidMinor`, `debtMinor`.
- **Цена за кг и начальный долг** ставит админ в карточке клиента («Клиенты» → карандаш). Начальный долг это сколько клиент был должен, когда рейсы начали вести здесь (предоплата со знаком минус); он задаётся один раз, как начальный остаток кассы. В файле списка клиентов после телефона могут стоять ещё две колонки: цена за кг и начальный долг (`707,Карим,7 999,"1,5","1200,50"`).
- **Кто что делает.** Админ всё и в любое время: правит накладную прибывшего рейса, меняет номер рейса и дату прибытия, возвращает рейс на шаг назад, удаляет рейс без грузов. Завсклад (роль `warehouse`) создаёт рейсы, ведёт шапку, отмечает «выехала» и «прибыл» и вносит грузы, пока рейс не прибыл: завсклад со складом (поле «Склад» в «Людях») только грузы своего склада (`403 warehouse_forbidden`), завсклад «Все склады» любого. Владелец смотрит. Кассиры в раздел не заходят: им нужен только долг клиента, и он есть в кассе.
- **Завсклад не видит кассу.** Остатки, журнал, итоги, категории и сверки для роли `warehouse` закрыты (`403`): каждому новому адресу API эта роль запрещена, пока адрес сам не разрешит (`config: { warehouse: true }`).
- **Расходы рейса.** Владелец и админ видят в «Итоге фуры», сколько касса потратила на рейс (расходы с этим номером рейса) и сколько остаётся от суммы грузов.
- **История.** Всё, что сделали с рейсом и его строками (кто, когда, что было и что стало), пишется в `trip_changes` в той же транзакции; строки истории нельзя изменить или удалить (база не даёт). Удалённая строка груза и удалённый рейс остаются в таблицах, скрытыми. `GET /api/trips/:number/history` (админ и владелец).
- **API.** `GET /api/trips` (список, `limit`, `before`), `POST /api/trips`, `GET`/`PATCH`/`DELETE /api/trips/:number` (шапка: `direction`, `loadingDay`, `departureDay`, ...), `POST /api/trips/:number/status` (`status`, `arrivalDay`), `POST /api/trips/:number/cargo` (`id` делает экран: строка, отправленная дважды, сохраняется один раз), `PUT`/`DELETE /api/trips/:number/cargo/:id`. Каждое изменение отвечает рейсом целиком, как он есть после него.
- **Чего пока нет:** ввода грузов без связи (раздел работает только при связи с сервером), сообщений в Telegram о рейсах и выгрузки накладной в Excel.

## Отчёты по долгам

Раздел «Отчёты» есть там же, где «Сборные грузы» (настройка `WAREHOUSES`), и виден кассирам всех касс, главному кассиру, админу и владельцу; завскладу не виден. Это отчёт по долгам клиентов за день кассы, четыре картинки (в последний день месяца пять), которые компания раньше каждый вечер собирала руками из картотеки Excel. Теперь он считается из тех же данных, что и долг клиента: рейсы, журнал кассы, история из картотеки. Код: `server/src/debt-report.ts` (расчёт), `server/src/debts.ts` (адреса и закрытия дней), `server/src/xlsx.ts` (книга Excel), миграция `0027_debt_closings.sql`; на экране `web/src/DebtReports.tsx`, слова в `web/src/debt-report.ts`, вид картинок и PNG в `web/src/report-picture.ts`.

- **День и с чем сравнить.** Отчёт строится на конец выбранного дня кассы и сравнивает его с днём перед ним. После выходных в поле «Сравнить с днём» ставят последний рабочий день: тогда отчёт за несколько дней, и в примечании движение расписано по дням. Самый длинный период 92 дня. `GET /api/debts/report?day=2026-11-16&since=2026-11-15` (без `day` сегодня, без `since` день перед `day`).
- **1. Изменение долга.** Долг всех клиентов на оба дня, сколько начислено (рейсы, **прибывшие** в периоде) и сколько оплачено; кто оплатил и кому начислено, по восемь самых больших сумм полосками, остальные одной строкой. Оплата, принятая не главной кассой, помечена кассой («Ташкент»); главная касса это первая в `KASSAS`. В примечании: правки задним числом, движение по дням, кто закрыл долг, кто оплатил рейс в день прибытия или в течение недели, первая оплата в году или после перерыва в 30 дней, переход долга через круглую сумму (каждые 50 тыс. $).
- **2. Топ-30 должников.** Должник это клиент с долгом больше 1 $ (предоплата в должники не попадает, но в общий долг входит). В строке место, долг, изменение за период и дата последней оплаты: красным, если оплаты нет 30 дней и больше. В примечании доля топ-30 в общем долге, кто вышел из списка и кто вошёл и почему, кто близко к 30 дням (от 21 дня).
- **3. Долго не платят.** Долг больше 500 $ и последняя оплата 30 и больше дней назад; у клиента без единой оплаты дни считаются от начала истории (первое января года, с которого она ведётся). Плашка дней красная от 90 дней, дата последнего рейса красная, если клиент получил груз в периоде отчёта.
- **4. Контроль по месяцам.** Тот же лист, что в «Клиентах», но до выбранного дня. Остаток на конец последнего месяца должен равняться долгу всех клиентов на этот день до цента; если нет, под таблицей предупреждение.
- **Закрытие дня и правки задним числом.** День кассы закрывается сам в 03:00 по Москве, и в этот момент Касса запоминает, сколько был должен каждый клиент (`debt_closings`; сервер смотрит раз в пять минут и перед каждым отчётом, пропущенные ночи закрывает, когда снова работает). Сами долги по-прежнему нигде не хранятся. Следующий отчёт пересчитывает прошлый день заново и сравнивает с запомненным: если запись прошлого дня исправили или удалили, сумму перенесли с одного клиента на другого или рейс отметили прибывшим задним числом, примечание называет клиентов и суммы, а плитка «Долг на …» показывает пересчитанную цифру. Если закрытия того дня нет (до него отчёт ещё не открывали), так и написано. Запомненное не меняется (база не даёт).
- **Картинки.** Каждый блок можно сохранить в PNG («Скачать PNG», «Скачать все 4 картинки») или скопировать и вставить прямо в чат. Картинка всегда шириной 760 px с двойной плотностью и в тёмном оформлении, с телефона такая же, как с компьютера. На телефоне кнопка открывает «Поделиться», если браузер умеет отдавать туда файлы.
- **Excel «Не платят больше 7 дней».** Кнопка в том же разделе: клиенты с долгом от 1 $ и последней оплатой больше 7 дней назад, с телефоном, последней оплатой, последним рейсом и оплаченным за год; фильтр по шапке, итог, дни без оплаты цветом (8–29 жёлтый, 30–89 оранжевый, 90+ красный). `GET /api/debts/unpaid.xlsx?day=2026-11-16`. Книга пишется самим сервером, без дополнительных пакетов.
- **5. Динамика за месяц.** Только в отчёте за последний день месяца: долг всех клиентов по дням месяца (линия, подписаны конец, максимум и минимум) и «начислено / оплачено» по месяцам года столбиками, под каждым месяцем остаток на его конец в тыс. $. В обычный день её нет. Графики рисует `web/src/DebtDynamics.tsx`.
- **Чего пока нет:** отправки картинок в Telegram самой Кассой.

## Курс и доллары

Владелец считает всё в долларах. Рублёвая запись несёт курс (сколько рублей за 1 доллар, как в колонке «Курс» его таблицы), и по нему рубли переводятся в доллары: `доллары = рубли / курс`, до цента, целыми числами (сервер и база считают одинаково). Остатки кассы по-прежнему раздельные, по валютам: деньги считают руками по валютам. Доллары это перерасчёт для итогов, а не третий остаток.

- **Приход в рублях: курс обязателен.** Расход в рублях: курс можно ввести или пропустить. Доллары курса не имеют. Курс хранится целым, `rate_e4` (курс × 10 000, до 4 знаков после запятой), правится и попадает в историю изменений как часть записи.
- **Расход без курса** переводится по среднему курсу его дня: среднее арифметическое курсов рублёвых приходов этого дня кассы (с 03:00 до 03:00 по Москве, удалённые не в счёт). Оно считается при чтении, поэтому пока день идёт, оно двигается вместе с новыми приходами, а когда день кончился, меняется только если исправили приход того дня. Нет рублёвых приходов в этот день: берётся курс последнего рублёвого прихода до конца дня; нет и его: курса нет, и в итогах такой расход стоит в строке «без курса».
- **Журнал:** у каждой операции `rateE4`, `usdMinor` (сколько это в долларах, `null` пока нет курса) и `rateSource` (`own` свой курс, `day` средний курс дня, `null`). На экране у рублёвой записи под суммой «≈ 1 000,00 $ · курс 79,00».
- **Итоги:** в `GET /api/summary` добавлен блок `usd`: `incomeMinor`, `expenseMinor` (без передачи владельцу), `handoverMinor`, `resultMinor` (приход минус расход) и `withoutRate` (рублёвые записи без курса: сумма и число отдельно по приходу и расходу; в долларовые цифры они не входят). На экране это карточка «В долларах» над карточками валют.
- **Для кассира:** поле «Курс» видно при выбранных рублях и скрыто при долларах. В приходе оно обязательное и стартует с курса последней записи сегодняшнего дня (вчерашний не подставляется, чтобы устаревший курс не прошёл незамеченным). В расходе оно пустое и необязательное.
- Записи, внесённые до этой возможности, остаются без курса: в итогах они в строке «без курса».

## Журнал

**Где какой журнал.** У кассира и главного кассира журнал дня (раздел «Журнал»): свои записи правит и удаляет в течение суток. У админа журнал владельца (любой период, фильтры, удалённые, «История»), и там у каждой записи «Изменить» и «Удалить». У владельца тот же журнал без правки.

На компьютере (от 960 px) журнал это компактная таблица, строка на запись: время, кассир, операция, **Приход** и **Расход** отдельными колонками, **Курс** (свой курс записи или средний курс дня с пометкой «ср.»; сумма в долларах видна при наведении), «Подробности» (клиент, рейс, контрагент, сотрудник и серым комментарий, длинное обрезается «…», целиком при наведении). На телефоне записи остаются карточками.

- `GET /api/operations`: журнал, новые сверху, постранично. Кассир и админ видят записи всех кассиров (книга и ящик с деньгами одни, у каждой записи указано, кто её внёс), удалённых они не видят; смотрящий видит всё. Параметры (все необязательные): `from`, `to` (дни кассы `YYYY-MM-DD`, оба включены; одна граница без другой означает один этот день, без обеих сегодня), `currency` (`RUB`/`USD`), `type` (`income`/`expense`), `category`, `clientCode` (код целиком, без учёта регистра), `author` (логин кассира), `deleted` (только смотрящий), `limit` (1-100, по умолчанию 50), `cursor` (значение `nextCursor` из предыдущего ответа). Ответ: `{ from, to, operations, nextCursor }`, где `nextCursor` равен `null` на последней странице. **День кассы идёт с 03:00 до 03:00 по Москве** (UTC+3), то есть от полуночи до полуночи по UTC: запись в 01:00 ночи относится к дню, который заканчивается. Смену открывать и закрывать не нужно, сутки переворачиваются сами.
- `GET /api/cashiers` (смотрящий и админ): кто вносит записи (кассиры и админы) для фильтра, включая тех, у кого доступ отозван (их старые операции остаются в журнале).
- Смотрящий только читает: `POST /api/operations` для него отвечает `403`, в интерфейсе у него нет форм ввода. Свою запись автор (кассир, главный кассир) может изменить или удалить в течение суток после того, как её внёс: этого хватает, чтобы исправить свою ошибку. Через сутки кнопки «Изменить» и «Удалить» у записи пропадают, а сервер отвечает `403 change_window_closed`. Чужие записи кассир не меняет никогда (`403 forbidden`). Админ в режиме «Касса» видит эти кнопки у всех записей и может изменить или удалить любую запись в любое время; если это чужая запись или запись старше суток, в главную тему группы Telegram уходит сообщение «⚠️ Админ … изменил (удалил) запись кассира … от 05.03 11:30 МСК: Расход «…»» с «Было», «Стало» и причиной.
- Курсор непрозрачный и хранит время с микросекундами, поэтому записи в одну миллисекунду не теряются между страницами; курсор, который сервер не выдавал, даёт `400`. Нулевой символ в тексте (фильтры, комментарий, получатель, код клиента) тоже даёт `400`.
- Неожиданные сбои сервера отвечают `500` с фиксированным текстом `Internal error`: подробности только в логе сервера, текст ошибки базы клиенту не уходит.

## Итоги за период

- `GET /api/summary` (смотрящий и админ, кассир получает `403`): итоги периода по каждой валюте отдельно. Параметры: `from`, `to` (дни кассы, с 03:00 до 03:00 по Москве, `YYYY-MM-DD`, оба включены; одна граница означает один этот день, без обеих сегодня; `from` позже `to` даёт `400`). Ответ: `{ from, to, currencies: [{ currency, openingMinor, incomeMinor, expenseMinor, handoverMinor, closingMinor, expenseByCategory: [{ category, amountMinor }] }] }`. Обе валюты есть всегда (RUB первой), даже с нулями. `openingMinor` это остаток на начало первого дня (начальный остаток плюс все операции до него), `closingMinor` остаток на конец последнего дня. `expenseMinor` это все расходы, кроме передачи владельцу (она отдельно в `handoverMinor`: деньги ушли из кассы, но это не затраты), `expenseByCategory` его разбивка по всем категориям списка, с нулями, возврат клиенту отдельной строкой. Всегда `openingMinor + incomeMinor - expenseMinor - handoverMinor + differenceMinor = closingMinor`, где `differenceMinor` это разница, которую нашли сверки кассы за период (недостача отрицательна). Удалённые операции не входят ни в суммы, ни в остатки; исправленные считаются по тому, что в них записано сейчас. Суммы по разным валютам не складываются. Всё считается одним запросом (одним снимком базы), граница суток по Москве.
- На экране смотрящего это вкладка «Итоги» рядом с журналом: две даты и быстрые кнопки (сегодня, вчера, 7 дней, этот месяц), под ними карточка на каждую валюту.

## Сообщения в группу Telegram

Касса пишет в группу Telegram про записи тех категорий, у которых админ поставил отметку «Сообщать в группу Telegram» (раздел «Категории», поле `notifyGroup`): кто принял или выдал, сколько, по какому курсу, сколько это в долларах, код клиента, получатель, комментарий. Если такую запись исправили, приходит «Исправлено» с «Было» и «Стало» (и что изменилось, кроме суммы), кто исправил и почему; если удалили, приходит «Удалено». Запись, которую исправлением перевели в категорию без отметки, тоже сопровождается сообщением, а запись, которую исправлением перевели в категорию с отметкой, приходит как новая. Сразу отмечены все расходы и «Оплата от клиента» (и приходы, внесённые до категорий), остальные приходы не отмечены. Включается двумя настройками, `TELEGRAM_BOT_TOKEN` и `TELEGRAM_GROUP_CHAT_ID` (номер группы, минус в начале); без номера группы ничего не отправляется и не копится. Если в группе есть темы, `TELEGRAM_THREAD_INCOME` и `TELEGRAM_THREAD_EXPENSE` (номера тем) разводят приходы и расходы по ним; вид без темы идёт в главную тему. Шаги настройки: `docs/deploy-windows.md`, раздел 3.3.

**Две кассы: Москва и Андижан.** У каждой записи, сверки и начального остатка есть касса (`kassa`: `moscow` или `andijan`, миграция 0020; всё, что было раньше, московское). Москва ведёт рубли и доллары, Андижан только доллары (`400` на рубли, и правка не переводит андижанскую запись в рубли). Кто где работает, решает поле «Город» во вкладке «Люди»: человек с городом работает только в своей кассе (`403 kassa_forbidden` на чужую), человек «Везде» видит обе: касса записи выбирается над формой («Москва / Андижан» в полосе остатка), а журнал, итоги и сверки переключаются «Обе кассы / Москва / Андижан» (выбор помнит устройство, `localStorage` `kassa.scope`; в «Обе» остатки по каждой кассе отдельной строкой, у каждой записи метка «МСК» или «АНД»). Остатки, журнал, итоги и сверки показывают выбранную кассу (`GET /api/balances`, `/api/operations`, `/api/summary`, `/api/reconciliations` принимают `kassa`; без неё у человека с городом своя касса, у «Везде» в журнале, итогах и сверках обе вместе, каждая валюта отдельно). Форма андижанской кассы без выбора валюты и курса; сверка Андижана только в долларах и без карты. Сообщения андижанской кассы идут в тему `TELEGRAM_THREAD_ANDIJAN`, в 1С пишутся только приходы Москвы, в Google-таблице колонка «Касса». Начальный остаток: `kassa.ps1 set-opening-balance --kassa andijan --currency USD --amount ...`. Шаги: `docs/deploy-windows.md`, раздел 3.6.

**Кассы задаются настройкой.** Какие кассы есть у компании и какие деньги в каждой, говорит настройка `KASSAS` в файле настроек экземпляра: кассы по порядку через запятую, у каждой `id:ВАЛЮТА` или `id:ВАЛЮТА+ВАЛЮТА` (`RUB`, `USD`). Без неё кассы те же, что были: `moscow:RUB+USD,andijan:USD`. Пример для компании с тремя долларовыми кассами: `KASSAS=moscow:USD,andijan:USD,tashkent:USD`. Имена `moscow`, `andijan`, `tashkent` код знает сам («Москва», «Андижан», «Ташкент»), любой другой город пишется с названием: `fergana=Фергана:USD`. Первая касса в списке главная: в неё пишет человек «Везде», пока не выбрал другую, её приходы и расходы идут в темы `TELEGRAM_THREAD_INCOME` и `TELEGRAM_THREAD_EXPENSE`, и только её приходы пишутся в 1С, если не сказано иначе. `id` кассы это и «Город» человека и категории, и то, что хранит каждая запись, поэтому кассу, в которой уже есть записи, нельзя переименовать или убрать из `KASSAS`, как и убрать у неё валюту, в которой у неё есть записи: сервер тогда не запустится и скажет, чего не хватает (иначе эти деньги выпали бы из остатков; так же он остановит строку `KASSAS` чужой компании, попавшую не в тот файл). В базе названий касс больше нет (миграция 0023 сняла списки `moscow`/`andijan` и правило «в Андижане только доллары», оставив проверку формы `id`): какие валюты ведёт касса, проверяет сервер на каждой записи, правке и сверке. Экраны берут кассы с сервера (`GET /api/kassas`: `id`, название, метка, валюты, пишется ли в 1С) и помнят последний ответ на устройстве, чтобы открываться без связи; при трёх кассах переключатель говорит «Все» вместо «Обе кассы». Настройки по кассам называются по `id` кассы заглавными буквами: тема Telegram для всех сообщений кассы `TELEGRAM_THREAD_<ID>` (`TELEGRAM_THREAD_ANDIJAN`, `TELEGRAM_THREAD_TASHKENT`; касса без своей темы, кроме главной, пишет в главную тему группы; тема с именем кассы, которой нет, никуда не ведёт, и об этом пишется в журнале службы при запуске), кассы, чьи приходы от клиентов идут в 1С, `ONEC_KASSAS=moscow,tashkent`, и своя касса в базе 1С для такой кассы `ONEC_KASSA_KEY_<ID>` (без неё `ONEC_KASSA_KEY`; ключ с именем кассы, которой нет в `KASSAS`, или кассы, которая не пишется в 1С, не даёт серверу запуститься: приходы ушли бы не в ту кассу 1С). Если кассу убрали из `ONEC_KASSAS`, её приходы, ждавшие очереди, получают «Не записан», а уже записанный документ после правки прихода не переносится в чужую кассу 1С, а получает «Ошибку» для человека. Когда у нескольких касс одни и те же валюты (три долларовые), по деньгам их не отличить, поэтому касса называется явно: сообщение в Telegram от кассы без своей темы заканчивается строкой «Касса: Ташкент», форма и итог сверки говорят «Сверка кассы «Ташкент»», а в списке сверок всех касс у сверки стоит метка кассы; у Москвы с рублями и долларами и долларового Андижана всё как было. Команды админа берут кассы оттуда же: `--kassa` принимает `id` из `KASSAS`, `telegram-test` шлёт проверку и в тему каждой кассы, `onec-check` называет кассы 1С.

**Коды клиентов и списки категорий тоже свои у каждой компании.** Как пишется код клиента, говорит настройка `CLIENT_CODES`: `letter` (буква «А» и цифры, «А707»; так без настройки) или `digits` (только цифры, «707», до девяти цифр и необязательный хвост «-2»). При `digits` сервер не дописывает букву, код с буквой не принимает, экран «Клиенты» говорит «только цифры», а из файла списка берутся строки, начинающиеся с цифры (при `letter` такие строки по-прежнему пропускаются: это может быть номер строки таблицы). Задаётся до первого клиента: уже заведённые коды не переписываются. Миграция 0024 оставляет в таблице клиентов проверку формы, общей для обоих видов. Клиента в 1С при `digits` ищут по цифрам в начале названия контрагента. Списки категорий новой компании задаются файлом: `set-categories --file categories.json` делает списки приходов и расходов такими, как в файле, в его порядке; категория с тем же названием (или с кодом, названным в файле) остаётся и получает галочки и город из файла, новая добавляется, все остальные уходят в архив (ничего не удаляется). Отметку «Сообщать в группу Telegram» команда у существующих категорий не трогает. Категория прихода от клиента в файле называется по коду: `"code": "client_payment"`; только она идёт в 1С. Формат файла показывает справка команды (`npm run admin -- help`).

**Журнал в Google-таблице.** Касса сама копирует журнал в Google-таблицу (лист «Журнал»): строка на каждую запись с колонками «Дата и время (МСК)», «Кассир», «Операция», «Приход», «Расход», «Валюта», «Курс», «Клиент», «Рейс», «Контрагент», «Сотрудник», «Комментарий», «Статус», «ID записи». Суммы и курс записываются числами, поэтому их можно складывать. Исправление или удаление переписывает строку самой записи (статус «изменена» или «удалена»), новых строк не добавляет; у рублёвого расхода без своего курса стоит средний курс дня, и строка переписывается, когда приход того дня его меняет. Строки идут по очереди (`sheet_outbox`, номер строки каждой записи в `sheet_rows`, миграция 0019); если Google недоступен, ждут и уходят по порядку, а повторная попытка не добавит строку дважды (запись ищется по ID). Записи, сделанные до включения (но не раньше `GOOGLE_SHEET_FROM`), дописываются при запуске. Включается настройками `GOOGLE_SHEET_ID` и `GOOGLE_SHEETS_KEY_FILE` (ключ сервисного аккаунта Google, которому дан доступ «Редактор» к таблице), по желанию `GOOGLE_SHEET_FROM` (первый день, например `2026-10-14`) и `GOOGLE_SHEET_TAB`. Шаги: `docs/deploy-windows.md`, раздел 3.5.

- **Надёжность.** Сообщение пишется в таблицу `telegram_outbox` в той же транзакции, что и операция: нет операции, нет и сообщения, и наоборот. Отправляет их рабочий цикл внутри службы, по одному, в порядке записи. Telegram недоступен: операция записана, сообщение ждёт и уходит позже, паузы между попытками растут (15 с, 30 с, ... до 15 минут, а если Telegram просит подождать, ждём столько), порядок сохраняется (сообщение «удалено» не обгонит «внесено»). Через 60 неудачных попыток, а при постоянном отказе (бота убрали из группы, неверный номер: ответы 400, 401, 403, 404) сразу, сообщение получает статус `failed` и причину в `last_error`, очередь идёт дальше. Токен в журнал и в таблицу не попадает.
- **Команды администратора:** `telegram-chats` (какие чаты и темы видел бот: так находят номера) и `telegram-test` (пробное сообщение в каждую тему). Сервер должен доставать до `api.telegram.org`.
- **Что не делается:** вечернего итога и бота с командами нет (это тикеты #15 и #18 плана), историю до включения в группу не отправляет.

## Запись в 1С

Оплата от клиента (категория «Оплата от клиента») может сама попадать в 1С (база Cosmo) как приходный кассовый ордер «Оплата покупателя», так же, как кассовые книги заносились скриптами: касса «Москва», валюта «Доллар», статья ДДС «Оплата от покупателей», без НДС, одна строка расшифровки с договором, проводка Дт 5010 / Кт 6310. Сумма документа это доллары записи (рубли по курсу записи, доллары как есть), комментарий это код клиента (`А406`), «Принято от» это контрагент, дата это момент записи по Москве. Расходы и остальные приходы в 1С не идут.

- **Выключено по умолчанию.** `ONEC_MODE`: `off` (ничего не делает), `preview` (репетиция: читает 1С, пишет в таблицу `onec_outbox`, что было бы записано, в 1С не пишет ничего) или `live` (пишет). Остальные настройки: `ONEC_ODATA_URL`, `ONEC_ODATA_USER`, `ONEC_ODATA_PASSWORD`, `ONEC_ORGANIZATION_KEY`, `ONEC_KASSA_KEY`, `ONEC_CURRENCY_KEY`, необязательный `ONEC_CLIENTS` (коды через запятую: пишутся только эти клиенты, для первого боевого пробного). Прежние имена этих настроек (`COSMO_1C_MODE`, `COSMO_ODATA_URL`, `COSMO_ODATA_USER`, `COSMO_ODATA_PASSWORD`, `COSMO_1C_ORGANIZATION_KEY`, `COSMO_1C_KASSA_KEY`, `COSMO_1C_CURRENCY_KEY`, `COSMO_1C_CLIENTS`, `COSMO_1C_SEND`) читаются по-прежнему: файл настроек, написанный раньше, менять не нужно; если настройка есть под обоими именами, действует `ONEC_`.
- **Контрагента не выдумывает.** Код клиента из записи (`A245`, `а-245`, `А406 Жавид`) ищется среди контрагентов 1С по началу названия или по ИНН-номеру. Нет такого, несколько таких, нет договора, в коде нет номера вида А245: запись ждёт человека, в группу Telegram приходит одно сообщение, раз в 15 минут Касса пробует снова и пишет сама, когда в 1С всё исправлено. Контрагентов и договоры Касса не создаёт.
- **Надёжность.** Запись ставится в очередь в той же транзакции, что и операция. 1С не отвечает: паузы растут от 30 секунд до 15 минут. Ответ потерялся после создания: следующая попытка находит уже созданный документ (дата, касса, сумма, комментарий) и продолжает с ним, второй не создаётся. После проведения проводки перечитываются и сверяются (Дт 5010, Кт 6310 или 4010, сумма); не те проводки: статус `failed`, сообщение в группу, документ остаётся в 1С для человека.
- **Когда уходит в 1С: ночью.** `ONEC_SEND`: `night` (по умолчанию) или `now`. Ночью значит в 03:00 МСК, когда закрыт день кассы: весь день кассир может исправлять и удалять свои записи, а в 1С уходит последний вариант, и средний курс дня к этому времени окончательный. Исправление или удаление прихода, который уже в 1С, тоже уходит следующей ночью. В колонке «1С» такие приходы стоят как «Уйдёт в 03:00». Кнопка «Повторить» отправляет сразу. Если 1С ночью не отвечает, Касса пробует снова, как обычно.
- **Исправили или удалили в Кассе, значит и в 1С.** Исправленный приход (сумма, курс, код клиента) исправляет свой документ: тот же ПКО распроводится, в нём меняются сумма, контрагент, договор, и он проводится снова; проводки проверяются заново. Если исправили то, чего в документе нет (комментарий), документ не трогается. Удалённый приход (или приход, который стал не «Оплатой от клиента») распроводит свой документ и ставит пометку на удаление; совсем из 1С Касса ничего не удаляет, помеченное удаляет бухгалтер. Если приход снова стал оплатой клиента, Касса снимает свою пометку и проводит документ снова. Документ, который человек сам пометил на удаление в 1С, Касса не трогает («Ошибка»). Если 1С отказалась (например, закрыт период), приход получает «Ошибку» и в группу приходит сообщение. Приход, по которому админ нажал «Не записывать», так и остаётся незаписанным. Приходы, внесённые в репетиции, при включении `live` сами не записываются: нужные возвращают кнопкой «Повторить» или командой `onec-retry`. Миграция 0022 (состояние `removed`).
- **Колонка «1С» в журнале админа.** У каждого прихода клиента московской кассы видно, что с ним в 1С: «Записан» и номер ПКО, «В очереди», «Ждёт» (с причиной: нет контрагента, нет договора...), «Ошибка» (с причиной), «Не записан» (пропущен), «Репетиция», «Удалён в 1С» (документ распроведён и помечен на удаление) или «Не отправлялся» (внесён, когда запись в 1С была выключена). Кнопки «Повторить» (снова в очередь, без второго документа, если он уже создан) и «Не записывать». Фильтр «1С»: ошибки и ждут, в очереди, записаны, не отправлялись. Видит и нажимает только админ (`GET /api/operations` отдаёт поле `onec` и принимает `onec=written|waiting|problem|none` только ему; `POST /api/admin/onec/:id/retry` и `/skip`, остальным `403`).
- **Команды администратора:** `onec-check` (только чтение: отвечает ли 1С, принят ли логин, есть ли счета, статья, организация, касса и валюта из настроек), `onec-status [--limit N]`, `onec-retry --id N`, `onec-skip --id N`. Шаги включения: `docs/deploy-windows.md`, раздел 3.4.
- **Проверено** на поддельной 1С в тестах, на настоящей базе ещё нет.

## Telegram (Mini App)

Тот же сайт открывается внутри Telegram как Mini App. Браузерная версия от этого не зависит и работает полностью без Telegram (у людей в России он идёт через VPN). Код: `server/src/telegram.ts`, `web/src/telegram.ts`, `web/src/TelegramLink.tsx`.

- **Включается токеном бота.** В файле настроек сервера задайте `TELEGRAM_BOT_TOKEN=...` (токен от `@BotFather`) и перезапустите службу. Без него все ответы `/api/telegram/*` это `404 telegram_disabled`, и приложение работает как раньше. Токен секретный: он лежит только в файле настроек, читаемом службой и администраторами.
- **Вход.** Telegram при запуске передаёт данные запуска (`initData`) в адресе (`#tgWebAppData=...`). `POST /api/telegram/login` с телом `{ initData }` проверяет подпись по правилу Telegram (HMAC-SHA256 с ключом, выведенным из токена бота) и давность (не старше часа, не из будущего); подделанные или устаревшие данные получают `401`. Если Telegram-аккаунт привязан к логину, ответ тот же, что у входа по паролю, и cookie сессии; непривязанный аккаунт получает `403 telegram_not_linked` и ничего больше. Отозванный логин через Telegram не входит.
- **Привязка.** Человек входит в Mini App логином и паролем, в «Настройках» появляется кнопка «Привязать Telegram» (данные запуска есть только внутри Telegram). `POST /api/telegram/link` (нужна сессия) привязывает аккаунт к логину; один аккаунт Telegram к одному логину (`409 telegram_taken` иначе), у логина один аккаунт за раз (новая привязка заменяет прежнюю). `DELETE /api/telegram/link` отвязывает. `GET /api/me` отдаёт `telegramLinked`. Дальше Mini App входит сам.
- **Скрипт Telegram с чужого сайта не грузится совсем.** Приложению нужны только данные запуска из адреса и два сообщения Telegram («готово» и «на всю высоту»), они написаны прямо в `web/src/telegram.ts`.
- Вечерний итог и бот (#15, #18) этим билетом не сделаны.

## День кассы и сверка

Смен нет: кассир ничего не открывает и не закрывает, все вносят в одну общую книгу. **День кассы идёт с 03:00 до 03:00 по Москве**: кассиры работают до 24:00, иногда вносят до 01:00, и ночные записи принадлежат дню, который заканчивается; в 03:00 сутки переворачиваются сами (это полночь по UTC). Код: `server/src/cash-day.ts` (граница дня одним местом, для сервера и для SQL), `server/src/reconciliations.ts`, `migrations/0013_reconciliations.sql`, на экране `web/src/ReconcileBar.tsx` (админ) и `web/src/ReconciliationsList.tsx` (смотрящий).

- **Сверка кассы.** Раньше пересчёт наличных был частью закрытия смены, теперь это отдельное действие одного человека, главного кассира (роль `head_cashier`): кнопка «Сверить кассу» в «Журнале» (или раздел «Сверка» на нижней панели), когда угодно, лучше вечером. Он пересчитывает наличные и вводит, сколько денег лежит в кассе по каждой валюте (ноль допустим), Касса записывает за ним разницу и приводит книгу к насчитанному: недостача уменьшает остаток, излишек увеличивает. Ни кассиры, ни админ, ни владелец этой кнопки не видят. В форме два поля: «Остаток рублей» и «Остаток долларов» (в Андижане только доллары). Поле «Рубли на карте» было и убрано: карту не пересчитывают. Сервер его по-прежнему принимает (`cardMinor` в `POST /api/reconciliations`, колонка `card_minor`, миграция 0018), а старые сверки с картой показываются как были. Сразу после сверки в главную тему группы Telegram уходит сообщение в том виде, в каком его раньше писали руками:

  ```
  Кассада колган пул
  208.000₽. Рубль
  5.300$. Доллар
  ```

  Повторная отправка той же сверки (потерянный ответ) второго сообщения не даёт.
- `POST /api/reconciliations` (только главный кассир), тело `{ id, counted: [{ currency, amountMinor }, ...] }`: `id` (uuid) делает клиент, по одной сумме на каждую валюту (RUB и USD), целые минимальные единицы. Для каждой валюты система берёт расчётный остаток (что книга говорит об остатке кассы сейчас: начальный остаток плюс все записи плюс разницы прошлых сверок), насчитанный и разницу (насчитанный минус расчётный: минус это недостача, плюс излишек); остатки на это время удерживаются, чтобы ни одна запись не втиснулась между двумя цифрами. Ответ `201` и `{ reconciliation: { id, madeAt, madeBy, currencies: [{ currency, calculatedMinor, actualMinor, differenceMinor }] }, balances }`. Тот же `id` с теми же суммами от того же главного кассира отвечает `200` как в первый раз (потерянный ответ не считает кассу дважды), с другими суммами или от другого человека `409 reconciliation_id_conflict`. Кассир, админ и смотрящий получают `403`. Сверку можно делать сколько угодно раз, каждая считается от книги в том виде, как её оставила прошлая. Сверка не меняется и не удаляется (база не даёт).
- `GET /api/reconciliations` (смотрящий и админ): сверки, новые первыми. Страницы: `limit` (до 100) и `before` (время последней сверки прошлой страницы), в ответе `nextBefore`.
- **В итогах** разница сверок за период в `differenceMinor`, и по-прежнему `открытие + приход - расход - передача + разница = закрытие`; разница относится к дню, в котором сделана сверка. На экране смотрящего вкладка «Сверки» (список: кто, когда, по книге, насчитано, разница) и строка «Разница при сверке» в «Итогах».
- **Что стало со старыми сменами.** Закрытые смены, в которых был пересчёт, миграцией `0013` перенесены в сверки (с тем же `id`, временем закрытия и тем, кто закрыл), поэтому остатки и итоги прошлого не изменились. Таблицы `shifts` и `shift_balances` и колонка `operations.shift_id` остались как история и больше нигде не читаются; новые записи в смену не попадают. Прежний средний курс смены тоже больше не используется: расходы без курса считаются по среднему курсу дня (см. «Курс и доллары»), поэтому доллары таких старых расходов могли чуть сдвинуться. Записи, внесённые между 00:00 и 03:00, переехали на предыдущий день кассы.
- **Телефоны, у которых в очереди остались записи со сменой.** Поле `shiftId` в `POST /api/operations` принимается и игнорируется: запись без связи не отклоняется из-за того, что смен больше нет. Адреса `/api/shifts*` убраны.
- **Что решено без вас и можно поменять.** Менять и удалять запись может только её автор, также и админ (если нужно, чтобы админ правил чужие, это одно условие в `server/src/ledger.ts`, `changeOperation`). О результате сверки в группу Telegram Касса не пишет.


## Правка, удаление и история

- `PUT /api/operations/:id` (кассир или админ, и только автор записи): правка. Тело как у нового внесения, без `id`, плюс необязательная `reason` (до 500 символов). Заменяет редактируемые поля целиком: сумма, валюта, категория, получатель, код клиента, комментарий; что не прислано, очищается. **Тип (приход или расход), автор и время записи не меняются.** Те же правила проверки, что при внесении. Если ничего не изменилось, ничего не записывается и версия не растёт. Параметры в строке запроса не принимаются (`400`), чтобы причина не терялась молча: она передаётся только в теле.
- `DELETE /api/operations/:id` (кассир или админ, и только автор записи), тело необязательное: `{ reason? }`; пустое тело допустимо и при `Content-Type: application/json`, а параметры в строке запроса дают `400`. Удаление логическое: запись скрывается, физически остаётся. Восстановления нет. Повторный запрос безвреден.
- Остаток может уйти в минус и при правке с удалением: правка и удаление записей не проверяют остаток. Правки идут в одной транзакции под блокировкой обеих валют, поэтому две правки одной записи не перемешиваются.
- Текст (комментарий, получатель, код клиента, причина) обрезается по краям; одиночная половина суррогатной пары заменяется на U+FFFD ещё до сравнения и сохранения, чтобы повтор того же запроса не считался изменением. Идентификатор операции в путях `/api/operations/:id...` должен быть uuid в обычной записи, иначе `400` (форма `urn:uuid:...` не принимается).
- Время изменения берётся, когда до запроса дошла очередь (после блокировки), поэтому в истории оно не идёт назад.
- Другие ответы: `403` чужая запись или смотрящий, `404` нет такой записи, `409 operation_deleted` запись уже удалена, `409 type_cannot_change` попытка сменить тип.
- Ответ на правку и удаление: `{ operation, balances }`. У операции есть `revision` (сколько раз её меняли, 0 значит как записана), `deletedAt` и `deletedBy`.
- `GET /api/operations/:id/history` (смотрящий и админ): как записана операция (`created`) и каждое изменение (`changes`: версия, `edit` или `delete`, время, автор, причина, значения `before` и `after`). Кассир истории не получает, даже своей.
- Журнал: параметр `deleted` (`exclude` по умолчанию, `include`, `only`) только для смотрящего, кассиру `403`. Удалённые записи не входят в остатки, подсказки кодов клиентов и валюту по умолчанию.
- Повтор исходного внесения (потерянный ответ, офлайн-очередь) после правки или удаления отвечает `200` с текущим состоянием: сравнивается исходное содержимое, а не текущее. Операция и остатки в таком ответе прочитаны из одного снимка базы, поэтому правка, прошедшая параллельно, не даёт ответа из двух разных моментов.
- Гарантии на уровне базы (миграция `0004_corrections.sql`), независимо от приложения: операции нельзя физически удалить (`DELETE`, `TRUNCATE` запрещены), строки истории нельзя менять и удалять, операция меняется только вместе со следующей версией и строкой истории (проверяется при завершении транзакции), причём строка должна говорить правду: что было до (все шесть полей), `edit` или `delete` соответствует изменению, а у удаления время и автор совпадают с `deleted_at` и `deleted_by`. Удалённая операция неизменна, новая всегда начинается с версии 0 и не удалённой. Функции проверок читают таблицы по полным именам с закреплённым `search_path`, поэтому временная таблица с тем же именем их не подменит. Чтобы всё же почистить данные перед запуском, разработчик отключает триггеры сознательно.
- Известный предел: ожидание блокировки валюты не ограничено по времени, и каждый ожидающий занимает одно из 10 соединений пула. Правки и удаления делают единицы людей, одна занимает десятки миллисекунд; всплеск в сотни одновременных правок мог бы занять пул, и часть запросов получила бы `500`. Для кассы это недостижимо, поэтому очередь и таймаут не добавлялись.
- `GET /api/client-codes?prefix=`: ранее вводившиеся коды клиентов, последние первыми, без учёта регистра, не больше восьми.
- `GET /api/operations/defaults`: валюта, которой этот кассир пользовался последней (по умолчанию RUB).

## Работа без связи

Кассир может вносить приход и расход без интернета. Код: `web/src/queue.ts` (очередь), `queue-store.ts` (хранение на телефоне, IndexedDB), `QueueBanner.tsx` и `EntryStatus.tsx` (что видит кассир), `web/sw/sw.js` (запуск без сети).

- **Запись сначала на телефон, потом на сервер.** Каждое внесение кассира сохраняется в IndexedDB и только затем отправляется. Если сервер ответил в течение 3 секунд, всё как обычно: «Записано». Если связи нет, сервер ответил ошибкой или не отвечает дольше 3 секунд, запись остаётся на телефоне, форма очищается, под ней написано «Сохранено на телефоне, на сервер не ушло: …» с причиной и тем, что будет дальше, а внизу появляется жёлтая плашка «Не отправлено: N». Когда запись дошла до сервера, надпись под формой сама меняется на «Записано». Закрытое приложение и перезагрузка телефона записи не теряют. Если телефон не принял запись (хранилище переполнено или закрыто), форма ничего не очищает и говорит об этом: запись тогда есть только в форме, и повторное нажатие отправит её с тем же `id`. Если кассир нажал кнопку во второй форме, пока первая запись ещё идёт, вторая не принимается (форма просит подождать секунду и нажать ещё раз): иначе она затёрла бы первую на телефоне. Если сессия кончилась, а телефон не смог сохранить запись, форма остаётся на экране и пишет, что делать.
- **Отправка идёт сама, пока приложение открыто**: при появлении связи (событие `online`), при открытии приложения и возврате на экран, по таймеру (через 3, 10, 30, 60 секунд после неудач, дальше раз в минуту) и по кнопке «Отправить сейчас». Закрытое приложение ничего не отправляет (фоновой отправки нет, в Safari на iPhone её не существует), плашка так и пишет.
- **По порядку.** Записи уходят по одной, старые первыми: новая не обгоняет те, что ждут на телефоне. Отправка останавливается на первой записи, до сервера с которой не достучались.
- **Ровно один раз.** У записи с самого начала есть `id`, и он не меняется. Сервер сохраняет `id` один раз и на повтор отвечает «уже сохранено» (`200`), поэтому потерянный ответ или повторная отправка не создают дубль (см. «Приход, расход и остатки»). Ответ считается «сервер записал», только если он про эту запись: страница входа в Wi-Fi или прокси, ответившие `200`, запись с телефона не удаляют. Запросы не висят вечно: на отправку 10 секунд, на остальное 15.
- **Только под логином автора.** Сервер берёт автора из сессии, поэтому запись уходит, только пока в приложении вошёл тот, кто её внёс (проверяется перед каждой отправкой). Вместе с записью идёт заголовок `X-Kassa-As` с логином автора, и сервер отвечает `409 wrong_session`, если сессия чужая (другая вкладка вошла другим кассиром, пока шла отправка): запись не окажется на другом кассире. Записи других кассиров на этом телефоне видны под плашкой, и если человек уже не работает, их можно удалить с подтверждением. Выход при неотправленных записях предупреждает.
- **Сессия кончилась**: записи остаются на телефоне, экран входа пишет, сколько их ждёт, после входа они уходят сами.
- **Сервер отказал по содержанию** (данные, которые он не может принять, или чужая запись): запись не пропадает и не отправляется без конца. Она остаётся в списке плашки с причиной, с кнопками «Отправить снова» и «Удалить с телефона» (удаление нужно подтвердить). Запись, которую только что ввели и которую сервер сразу отклонил, на телефоне не остаётся: форма показывает причину, и сумму можно поправить.
- **Приложение открывается без связи.** Service worker (`sw.js`, его версию и список файлов вписывает сборка Vite) кладёт копию приложения на телефон целиком, а не по частям (файл, оказавшийся страницей входа в Wi-Fi или ответом прокси вместо скрипта, копию не принимает), и новая версия вступает в силу, только когда скачана целиком. Страницу он берёт у сервера, а если тот не ответил за 5 секунд или ответил ошибкой `5xx` (приложение обновляется, прокси говорит `502`/`503`/`504`), открывает копию с телефона. Всё под `/api/` не кэшируется никогда: остатки, журнал и записи всегда спрашиваются у сервера. Телефон помнит последнего вошедшего кассира, список категорий расхода и валюту последней записи (`localStorage`), поэтому расход можно внести и без связи, а форма открывается в валюте последней записи, сделанной на этом телефоне (в том числе ещё не отправленной). Ответ сервера о валюте нужен, только если телефон ничего не помнит, и он никогда не меняет валюту, когда кассир уже что-то ввёл или выбрал. Приложение просит у браузера не очищать его хранилище (`navigator.storage.persist()`).
- **Без связи недоступно**: остатки (на экране «Нет связи», рядом число неотправленных записей), журнал, правка, удаление, история.
- **Несколько вкладок** одного браузера делят очередь (`BroadcastChannel`, замок `navigator.locks` на отправку).
- **Известные пределы.** Время записи на сервере это время её получения, а не ввода: запись, внесённая без связи в 10:02 и дошедшая в 10:40, в журнале стоит на 10:40 (время ввода на телефоне хранится в очереди и видно в плашке, но на сервер пока не передаётся). Неотправленную запись нельзя исправить: ошибку исправляют в «Журнале», когда запись дойдёт, или удаляют запись с телефона и вносят заново. Проверки на повтор по смыслу (та же сумма, тот же код клиента) нет: если кассир не заметил, что запись уже внесена, и внёс её ещё раз, это две записи. То, что кассир удалил запись с телефона, сервер не узнаёт. Если сервер сохранил запись, а ответ потерялся, надпись «на сервер не ушло» может быть неверна: запись уже в журнале, повторная отправка дубля не создаст, поэтому перед удалением записи с телефона и повторным внесением нужно смотреть журнал. Первый запуск после обновления приложения при плохой связи может показать пустой экран, если страница дошла, а новые файлы нет: достаточно открыть приложение ещё раз. Страница, открытая до обновления, работает на прежней версии, пока её не откроют заново. Если в браузере нет IndexedDB совсем, записи живут только в памяти открытой страницы и пропадут при закрытии: приложение это пока не показывает. Заголовок `X-Kassa-As` сервер пока не требует (его нет у старых страниц), поэтому проверка автора действует только для страниц новой версии. Надёжность хранилища на iPhone проверяется на настоящем телефоне, установленном «на экран Домой» (тикет #13). По документации Apple, для сайтов в Safari хранилище может быть очищено после недели без использования, для приложения на экране «Домой» это ограничение не действует (не проверено).

## Развёртывание на сервере

Сервер владельца работает под Windows 10: службы Windows без Docker (приложение, PostgreSQL 16, Caddy с автоматическим HTTPS). Подробная инструкция с командами, проверкой после установки, резервными копиями, обновлением, откатом и разбором проблем: [docs/deploy-windows.md](docs/deploy-windows.md).

Скрипты лежат в `deploy/windows/` (PowerShell 5.1, он есть в каждой Windows 10) и `deploy/` (Node.js):

- установка: `setup.ps1` (папки, база, настройки, первая сборка), `download-tools.ps1` (WinSW и Caddy с проверкой SHA-256), `install-services.ps1` (службы, их учётные записи, брандмауэр, HTTPS), `power.ps1` (сон, часы), `kassa.ps1` (команды администратора с настройками машины);
- работа: `update.ps1` (обновление и откат одной командой, с копией базы перед ним и возвратом при сбое), `verify.ps1` (проверка всей установки), `uninstall-services.ps1`, `build.ps1`;
- копии: `backup.ps1` и `deploy/backup.mjs` (сжатая копия, ротация: ночные 14, перед обновлением 5, `-Status`), `restore.ps1` и `deploy/restore.mjs` (`-Check`: проверка копии в пробной базе; `-Replace`: замена рабочей базы с сохранением прежней, обе замены имён одной транзакцией; без одного из двух ничего не делает), `schedule-backup.ps1` (ночное задание в Планировщике);
- проверки: `lint.ps1` (сами скрипты без Windows), `deploy/check.mjs` (работающий сервер по адресу), `deploy/setup-database.mjs` (роль, база в UTF8, файл настроек).

Файл настроек вне репозитория: образец `deploy/kassa.env.example`. `npm run admin -w server -- migrate` применяет миграции базы отдельно от запуска сервера; код выхода 3: база не такая, как нужно (не UTF8, изменена более новой версией), 4: миграция не применилась и ничего не изменилось (скрипт обновления возвращает прежнюю версию), 1: другая ошибка, возможно, часть миграций уже применена. Сервер отказывается работать на базе, которую изменила более новая версия (иначе остатки могли бы быть неверными; аварийный выход `ALLOW_NEWER_SCHEMA=1`), и на базе не в UTF8.

## Сборка и запуск как в проде

```sh
npm run build
DATABASE_URL=... npm start   # сервер отдаёт и API, и web/dist на одном адресе
```

На HTTPS задайте `NODE_ENV=production` (или `COOKIE_SECURE=true`), иначе cookie сессии не получит флаг `Secure`. По умолчанию сервер слушает только `127.0.0.1` (порт `3000`). Внутри контейнера или за прокси на другой машине задайте `HOST=0.0.0.0`, порт меняется через `PORT`. Маршруты приложения не должны содержать точку: запрос пути с расширением считается запросом файла и при его отсутствии получает честный `404`, а не оболочку.

## Тесты

Тесты ходят только в публичный HTTP API сервера и работают с настоящей PostgreSQL: подмен базы нет. Для каждого теста создаётся и потом удаляется отдельная база.

1. Нужна роль PostgreSQL-суперпользователь (как в CI): тесты создают и удаляют базы, а тесты `deploy/setup-database.mjs` ещё и роли. Адрес сервера задаётся переменной `TEST_DATABASE_URL`, по умолчанию `postgres://kassa_test:kassa_test@localhost:5432/postgres`. Создать такую роль можно так:

   ```sh
   psql -U postgres -c "CREATE ROLE kassa_test LOGIN SUPERUSER PASSWORD 'kassa_test'"
   ```

2. Запуск:

   ```sh
   npm test               # тесты сервера (HTTP API на настоящей базе) и веба (очередь внесения)
   npm run typecheck      # проверка типов сервера и веба
   npm run test:e2e       # сквозные тесты в настоящем браузере: собирает веб и гоняет работу без связи
   ```

   Для `test:e2e` нужен Chromium: `npx playwright install chromium` (или переменная `CHROMIUM_PATH` с путём к нему). Тестам копий базы (`server/test/backup-scripts.test.ts`) нужны `pg_dump` и `pg_restore` версии не ниже сервера (в Ubuntu пакет `postgresql-client-16`) в `PATH`. Тестам скриптов PowerShell (`server/test/powershell-scripts.test.ts`: «выдуманная машина» с настоящим git-репозиторием и заглушками служб и `icacls`) нужен `pwsh` (PowerShell 7) в `PATH`; без него эти тесты пропускаются. Они показывают, что решают скрипты, но не как ведёт себя Windows PowerShell 5.1 и сама Windows.

Если прогон оборвался посередине, могли остаться базы `kassa_test_...`: их можно удалить командой `DROP DATABASE`.

## CI

GitHub Actions (`.github/workflows/ci.yml`) на каждый push в любую ветку. Задание `check` (Ubuntu): проверка типов, тесты на PostgreSQL 16, сборка, проверка скриптов `deploy/windows` (`lint.ps1`), сквозные тесты в браузере (`npm run test:e2e`). Задание `windows` (`windows-latest`, Windows PowerShell 5.1): ставит PostgreSQL 16 установщиком, прогоняет `setup.ps1`, `download-tools.ps1`, `install-services.ps1`, ночное задание копий, `restore.ps1`, `update.ps1`, `verify.ps1`, `uninstall-services.ps1` и ждёт, что всё проходит. Перезагрузки оно проверить не может: это делается руками на настоящем сервере (инструкция, раздел 4.4). Когда задание писали, GitHub не запускал на этом репозитории ни одно задание (они заканчивались за три секунды без шагов), поэтому ни разу не видело, что у `windows` получится на самом деле.
