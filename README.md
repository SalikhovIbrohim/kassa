# Касса

Учёт наличных (кассовая книга) для небольшой грузоперевозочной фирмы: кассиры записывают приход и расход в одну общую книгу (смен нет, день сам меняется в 03:00 по Москве), один из них, админ, сверяет кассу с пересчитанными наличными, владелец только смотрит. Сайт (PWA) для iPhone и ноутбука, позже Telegram. Подробности в спеке: issue #1.

## Состав

- `server/`: сервер на Node.js и TypeScript (Fastify), база PostgreSQL. Отдаёт API (`/api/...`) и собранное веб-приложение.
- `web/`: PWA-оболочка на React и TypeScript (Vite).

## Что нужно

- Node.js 22.12 или новее и npm.
- PostgreSQL 16 (локально или в контейнере).

## Запуск для разработки

```sh
npm install
cp .env.example .env        # затем поправьте DATABASE_URL под свою базу
```

Сервер читает настройки из переменных окружения (см. `.env.example`). Например:

```sh
DATABASE_URL=postgres://kassa:kassa@localhost:5432/kassa npm run dev:server   # API на :3000
npm run dev:web                                                               # веб на :5173, /api идёт на :3000
```

Проверка работоспособности: `GET /api/health` отвечает `200` и `{"status":"ok","database":"up"}`, а если база недоступна, `503`.

## Пользователи и вход

Входят логином и паролем. Пользователей заводит разработчик вручную, интерфейса для этого нет. Роли: `cashier` (кассир), `admin` (админ: стоит выше владельца, делает всё, что кассир, сверяет кассу кнопкой «Сверить кассу», см. «День кассы и сверка», и видит и решает всё, что владелец: итоги, историю правок, удалённые записи, списки категорий) и `viewer` (смотрящий, владелец, только читает). Экран админа это два режима: «Касса» (экран кассира с кнопкой сверки) и «Управление» (экран владельца).

```sh
npm run build                                   # один раз, команды берутся из server/dist
export DATABASE_URL=postgres://...              # в PowerShell: $env:DATABASE_URL = "postgres://..."

npm run admin -w server -- create-user --login ivan --role cashier --name "Иван Петров"
npm run admin -w server -- create-user --login anvar --role admin --name "Анвар"
npm run admin -w server -- create-user --login owner --role viewer
npm run admin -w server -- list-users
npm run admin -w server -- set-role --login ivan --role admin       # меняет роль (cashier, admin, viewer); действует со следующего запроса, записи остаются
npm run admin -w server -- revoke-user --login ivan      # закрывает доступ и все сессии
npm run admin -w server -- restore-user --login ivan     # возвращает доступ, входить нужно заново
npm run admin -w server -- reset-password --login ivan   # новый пароль, все сессии закрываются
npm run admin -w server -- set-opening-balance --currency RUB --amount 12345.67   # начальный остаток
npm run admin -w server -- balances                      # остатки по валютам: начальный + приходы - расходы + разницы сверок
```

Пароль не передаётся в командной строке: его спросят в терминале (символы не показываются) или возьмут из переменной `KASSA_PASSWORD`. Минимум 8 символов. Логин не зависит от регистра букв. На разработке без сборки можно `npm run admin:dev -w server -- ...`.

Как это устроено:

- `POST /api/login` (`login`, `password`) выдаёт сессию в cookie `kassa_session` (HttpOnly, SameSite=Lax, `Secure` на HTTPS). `GET /api/me` говорит, кто вошёл, или отвечает `401`. `POST /api/logout` закрывает сессию этого устройства.
- Сессия живёт 90 дней без использования и продлевается, пока человек пользуется приложением (`SESSION_DAYS`). Пароль нужен при первом входе и по истечении срока.
- Пароли хранятся только хешем (scrypt), в базе лежит хеш токена сессии, а не сам токен.
- Защита от подбора пароля. После 5 неверных паролей подряд для логина вход откладывается: ответ `429` с `Retry-After` и `{ error: "too_many_attempts", retryAfterSeconds }`, ожидание растёт 30 с, 1 мин, 2 мин, 4 мин и так до 15 минут. Попытки во время ожидания отклоняются сразу и ожидание не увеличивают. Верный пароль обнуляет счётчик, через 30 минут без попыток счётчик забывается сам. Несуществующий логин ограничивается так же, по ответам отличить его нельзя. Уже выданные сессии не затрагиваются. Отдельный, более мягкий счётчик (20 неудач) ведётся по адресу клиента: он останавливает перебор многих логинов с одного адреса. Успешный вход его не обнуляет.
- Счётчики хранятся в памяти сервера: после перезапуска службы они пусты. Посторонний может раз в интервал отправить одну неверную попытку на логин кассира и удерживать ему ожидание, до 15 минут: это цена решения «задержка, а не блокировка».
- **За обратным прокси (Caddy) обязательно задайте `TRUST_PROXY`**, например `TRUST_PROXY=127.0.0.1`: только тогда адрес клиента берётся из `X-Forwarded-For`. Без этой настройки заголовок игнорируется (его может подделать любой), и все клиенты за прокси выглядят одним адресом. Тогда один посторонний за 20 неверных попыток выставит ожидание для всех входов, включая владельца. Если сервер видит `X-Forwarded-For` на локальном соединении без `TRUST_PROXY`, он один раз пишет предупреждение в журнал.
- Счётчик логина привязан к учётной записи, а не к написанию: «Ivan», «ivan » и «İvan» (если база читает их как один логин) делят один счётчик.
- Одновременно выполняется не больше 4 проверок пароля (каждая около 100 мс и 32 МБ памяти) и ещё 16 ждут очереди; остальные получают `503` с `Retry-After: 2`, сервер не падает и память не растёт.
- Миграции базы (`server/migrations/*.sql`) применяются при старте сервера и перед командами администратора.
- Для кода следующих тикетов: хуки `app.authenticate` (только вошедшие, кладёт пользователя в `request.user`) и `app.requireRole("cashier", "admin")` ставятся в `onRequest` маршрута: права проверяются раньше, чем тело запроса.

## Приход, расход и остатки

Деньги хранятся целым числом минимальных единиц (копейки, центы), валюты RUB и USD ведутся отдельно, без пересчёта.

- `POST /api/operations` (кассир или админ). Приход: `{ id, type: "income", amountMinor, currency, rateE4?, category?, clientCode?, comment? }`. Расход: `{ id, type: "expense", amountMinor, currency, rateE4?, category, recipient?, clientCode?, comment? }`; `rateE4` это курс (рублей за 1 доллар), умноженный на 10 000 (79,5 это `795000`), от 1 до 1000: у прихода в рублях обязателен, у расхода в рублях необязателен, у долларов запрещён (`400`), см. «Курс и доллары»; `category` это код категории из списков владельца (см. «Категории»): у расхода обязательна, у прихода без неё запись считается оплатой от клиента (`client_payment`, так пишут телефоны, обновлённые не до конца); `clientCode` обязателен, если у категории отмечено «нужен код клиента» (оплата от клиента, возврат клиенту), и запрещён у остальных (`400`). Поле `shiftId` прежних телефонов принимается и игнорируется (смен больше нет, см. «День кассы и сверка»). `id` (uuid в обычной записи 8-4-4-4-12, регистр любой) создаёт клиент: повторная отправка той же операции отвечает `200` и не создаёт дубль, тот же `id` с другим содержимым или от другого кассира даёт `409`. Ответ: сама операция и текущие остатки. Остаток не ограничивает расход: касса ведётся параллельно с таблицей без ограничений, и расход больше остатка записывается, остаток тогда показывается ниже нуля (красным). Отказа «не хватает денег» нет ни при внесении, ни при правке и удалении. Повтор уже принятого расхода отвечает `200`.
- `GET /api/categories` (любой вошедший): `{ categories, income, all }`. `categories` это действующие категории расхода (ответ, который знают прежние телефоны), `income` действующие категории прихода, `all` все категории обоих видов, в том числе архивные (журнал должен называть и их). У каждой: `code`, `kind`, `label`, `sortOrder`, `archived`, `requiresClient`, `countsAsCost`. См. «Категории».
- `GET /api/balances`: остаток по каждой валюте (начальный остаток + приходы - расходы + разницы, найденные при сверках кассы, см. «День кассы и сверка»), доступен любому вошедшему.

## Категории

Категории прихода и расхода лежат в таблице `categories`, а не в коде, и ими управляет владелец (смотрящий) со своего экрана: вкладка «Категории». Кассир в формах выбирает категорию из выпадающего списка.

- **Код и подпись.** Операция хранит `code` категории; он выдаётся один раз и не переиспользуется. Подпись владелец может переписать, старые записи тогда читаются с новой подписью.
- **Что можно:** добавить категорию (в конец её списка), переименовать, отметить «нужен код клиента», двигать вверх и вниз, убрать в архив и вернуть. Удалить нельзя: старые записи её помнят. Архивная категория не предлагается в новых записях, но остаётся в журнале, в итогах (пока в ней что-то есть за период) и в правке той записи, у которой она уже стоит. Последнюю действующую категорию списка в архив убрать нельзя (`409 last_category`). Одинаковые названия в одном списке (без учёта регистра) не принимаются (`409 category_exists`).
- **API владельца (смотрящий и админ):** `POST /api/admin/categories` с `{ kind: "income"|"expense", label, requiresClient? }` и `PATCH /api/admin/categories/:code` с любым из `label`, `requiresClient`, `archived`, `move: "up"|"down"`. Ответ: `{ category, all }`.
- **Признак «нужен код клиента»** у категории решает, спрашивает ли форма код клиента: у «Оплата от клиента» и «Возврат клиенту» он есть, у остальных его нет, и сервер его в них не принимает. Признак «не затрата бизнеса» (`countsAsCost`) есть только у «Передача владельцу»: она вычитается из остатка, но в итогах стоит отдельной строкой, а не в расходе. Его владелец не меняет.
- **Первые списки.** Расход: шесть прежних категорий (их коды уже стоят в записях) и ещё девятнадцать из таблицы владельца (оплата фура, таможня, обеды, квартира, офис, склад и другие). Приход: оплата от клиента, взяли долг, приход от субаренды, сотрудник вернул долг, прочее. Это предложение для начала: владелец правит списки сам.
- **Записи без категории.** Приходы, внесённые до категорий, хранятся без неё и читаются как «Приход» (оплата клиента).
- **Телефон без связи.** Последние списки копируются в память телефона. Если списков нет совсем, приход всё равно можно внести (как оплату клиента); расход без списка внести нельзя.
- **Итоги:** `expenseByCategory` теперь перечисляет все действующие категории затрат (с нулями) и архивные, у которых за период что-то есть.

## Курс и доллары

Владелец считает всё в долларах. Рублёвая запись несёт курс (сколько рублей за 1 доллар, как в колонке «Курс» его таблицы), и по нему рубли переводятся в доллары: `доллары = рубли / курс`, до цента, целыми числами (сервер и база считают одинаково). Остатки кассы по-прежнему раздельные, по валютам: деньги считают руками по валютам. Доллары это перерасчёт для итогов, а не третий остаток.

- **Приход в рублях: курс обязателен.** Расход в рублях: курс можно ввести или пропустить. Доллары курса не имеют. Курс хранится целым, `rate_e4` (курс × 10 000, до 4 знаков после запятой), правится и попадает в историю изменений как часть записи.
- **Расход без курса** переводится по среднему курсу его дня: среднее арифметическое курсов рублёвых приходов этого дня кассы (с 03:00 до 03:00 по Москве, удалённые не в счёт). Оно считается при чтении, поэтому пока день идёт, оно двигается вместе с новыми приходами, а когда день кончился, меняется только если исправили приход того дня. Нет рублёвых приходов в этот день: берётся курс последнего рублёвого прихода до конца дня; нет и его: курса нет, и в итогах такой расход стоит в строке «без курса».
- **Журнал:** у каждой операции `rateE4`, `usdMinor` (сколько это в долларах, `null` пока нет курса) и `rateSource` (`own` свой курс, `day` средний курс дня, `null`). На экране у рублёвой записи под суммой «≈ 1 000,00 $ · курс 79,00».
- **Итоги:** в `GET /api/summary` добавлен блок `usd`: `incomeMinor`, `expenseMinor` (без передачи владельцу), `handoverMinor`, `resultMinor` (приход минус расход) и `withoutRate` (рублёвые записи без курса: сумма и число отдельно по приходу и расходу; в долларовые цифры они не входят). На экране это карточка «В долларах» над карточками валют.
- **Для кассира:** поле «Курс» видно при выбранных рублях и скрыто при долларах. В приходе оно обязательное и стартует с курса последней записи сегодняшнего дня (вчерашний не подставляется, чтобы устаревший курс не прошёл незамеченным). В расходе оно пустое и необязательное.
- Записи, внесённые до этой возможности, остаются без курса: в итогах они в строке «без курса».

## Журнал

- `GET /api/operations`: журнал, новые сверху, постранично. Кассир и админ видят записи всех кассиров (книга и ящик с деньгами одни, у каждой записи указано, кто её внёс), удалённых они не видят; смотрящий видит всё. Параметры (все необязательные): `from`, `to` (дни кассы `YYYY-MM-DD`, оба включены; одна граница без другой означает один этот день, без обеих сегодня), `currency` (`RUB`/`USD`), `type` (`income`/`expense`), `category`, `clientCode` (код целиком, без учёта регистра), `author` (логин кассира), `deleted` (только смотрящий), `limit` (1-100, по умолчанию 50), `cursor` (значение `nextCursor` из предыдущего ответа). Ответ: `{ from, to, operations, nextCursor }`, где `nextCursor` равен `null` на последней странице. **День кассы идёт с 03:00 до 03:00 по Москве** (UTC+3), то есть от полуночи до полуночи по UTC: запись в 01:00 ночи относится к дню, который заканчивается. Смену открывать и закрывать не нужно, сутки переворачиваются сами.
- `GET /api/cashiers` (смотрящий и админ): кто вносит записи (кассиры и админы) для фильтра, включая тех, у кого доступ отозван (их старые операции остаются в журнале).
- Смотрящий только читает: `POST /api/operations` для него отвечает `403`, в интерфейсе у него нет форм ввода. Менять и удалять запись может только её автор, также и админ: чужие записи в журнале видны без кнопок «Изменить» и «Удалить».
- Курсор непрозрачный и хранит время с микросекундами, поэтому записи в одну миллисекунду не теряются между страницами; курсор, который сервер не выдавал, даёт `400`. Нулевой символ в тексте (фильтры, комментарий, получатель, код клиента) тоже даёт `400`.
- Неожиданные сбои сервера отвечают `500` с фиксированным текстом `Internal error`: подробности только в логе сервера, текст ошибки базы клиенту не уходит.

## Итоги за период

- `GET /api/summary` (смотрящий и админ, кассир получает `403`): итоги периода по каждой валюте отдельно. Параметры: `from`, `to` (дни кассы, с 03:00 до 03:00 по Москве, `YYYY-MM-DD`, оба включены; одна граница означает один этот день, без обеих сегодня; `from` позже `to` даёт `400`). Ответ: `{ from, to, currencies: [{ currency, openingMinor, incomeMinor, expenseMinor, handoverMinor, closingMinor, expenseByCategory: [{ category, amountMinor }] }] }`. Обе валюты есть всегда (RUB первой), даже с нулями. `openingMinor` это остаток на начало первого дня (начальный остаток плюс все операции до него), `closingMinor` остаток на конец последнего дня. `expenseMinor` это все расходы, кроме передачи владельцу (она отдельно в `handoverMinor`: деньги ушли из кассы, но это не затраты), `expenseByCategory` его разбивка по всем категориям списка, с нулями, возврат клиенту отдельной строкой. Всегда `openingMinor + incomeMinor - expenseMinor - handoverMinor + differenceMinor = closingMinor`, где `differenceMinor` это разница, которую нашли сверки кассы за период (недостача отрицательна). Удалённые операции не входят ни в суммы, ни в остатки; исправленные считаются по тому, что в них записано сейчас. Суммы по разным валютам не складываются. Всё считается одним запросом (одним снимком базы), граница суток по Москве.
- На экране смотрящего это вкладка «Итоги» рядом с журналом: две даты и быстрые кнопки (сегодня, вчера, 7 дней, этот месяц), под ними карточка на каждую валюту.

## Сообщения в группу Telegram

Касса пишет в группу Telegram про записи тех категорий, у которых владелец поставил отметку «Сообщать в группу Telegram» (вкладка «Категории», поле `notifyGroup`): кто принял или выдал, сколько, по какому курсу, сколько это в долларах, код клиента, получатель, комментарий. Если такую запись исправили, приходит «Исправлено» с «Было» и «Стало» (и что изменилось, кроме суммы), кто исправил и почему; если удалили, приходит «Удалено». Запись, которую исправлением перевели в категорию без отметки, тоже сопровождается сообщением, а запись, которую исправлением перевели в категорию с отметкой, приходит как новая. Сразу отмечены все расходы и «Оплата от клиента» (и приходы, внесённые до категорий), остальные приходы не отмечены. Включается двумя настройками, `TELEGRAM_BOT_TOKEN` и `TELEGRAM_GROUP_CHAT_ID` (номер группы, минус в начале); без номера группы ничего не отправляется и не копится. Если в группе есть темы, `TELEGRAM_THREAD_INCOME` и `TELEGRAM_THREAD_EXPENSE` (номера тем) разводят приходы и расходы по ним; вид без темы идёт в главную тему. Шаги настройки: `docs/deploy-windows.md`, раздел 3.3.

- **Надёжность.** Сообщение пишется в таблицу `telegram_outbox` в той же транзакции, что и операция: нет операции, нет и сообщения, и наоборот. Отправляет их рабочий цикл внутри службы, по одному, в порядке записи. Telegram недоступен: операция записана, сообщение ждёт и уходит позже, паузы между попытками растут (15 с, 30 с, ... до 15 минут, а если Telegram просит подождать, ждём столько), порядок сохраняется (сообщение «удалено» не обгонит «внесено»). Через 60 неудачных попыток, а при постоянном отказе (бота убрали из группы, неверный номер: ответы 400, 401, 403, 404) сразу, сообщение получает статус `failed` и причину в `last_error`, очередь идёт дальше. Токен в журнал и в таблицу не попадает.
- **Команды администратора:** `telegram-chats` (какие чаты и темы видел бот: так находят номера) и `telegram-test` (пробное сообщение в каждую тему). Сервер должен доставать до `api.telegram.org`.
- **Что не делается:** вечернего итога и бота с командами нет (это тикеты #15 и #18 плана), историю до включения в группу не отправляет.

## Запись в 1С

Оплата от клиента (категория «Оплата от клиента») может сама попадать в 1С (база Cosmo) как приходный кассовый ордер «Оплата покупателя», так же, как кассовые книги заносились скриптами: касса «Москва», валюта «Доллар», статья ДДС «Оплата от покупателей», без НДС, одна строка расшифровки с договором, проводка Дт 5010 / Кт 6310. Сумма документа это доллары записи (рубли по курсу записи, доллары как есть), комментарий это код клиента (`А406`), «Принято от» это контрагент, дата это момент записи по Москве. Расходы и остальные приходы в 1С не идут.

- **Выключено по умолчанию.** `COSMO_1C_MODE`: `off` (ничего не делает), `preview` (репетиция: читает 1С, пишет в таблицу `onec_outbox`, что было бы записано, в 1С не пишет ничего) или `live` (пишет). Остальные настройки: `COSMO_ODATA_URL`, `COSMO_ODATA_USER`, `COSMO_ODATA_PASSWORD`, `COSMO_1C_ORGANIZATION_KEY`, `COSMO_1C_KASSA_KEY`, `COSMO_1C_CURRENCY_KEY`, необязательный `COSMO_1C_CLIENTS` (коды через запятую: пишутся только эти клиенты, для первого боевого пробного).
- **Контрагента не выдумывает.** Код клиента из записи (`A245`, `а-245`, `А406 Жавид`) ищется среди контрагентов 1С по началу названия или по ИНН-номеру. Нет такого, несколько таких, нет договора, в коде нет номера вида А245: запись ждёт человека, в группу Telegram приходит одно сообщение, раз в 15 минут Касса пробует снова и пишет сама, когда в 1С всё исправлено. Контрагентов и договоры Касса не создаёт.
- **Надёжность.** Запись ставится в очередь в той же транзакции, что и операция. 1С не отвечает: паузы растут от 30 секунд до 15 минут. Ответ потерялся после создания: следующая попытка находит уже созданный документ (дата, касса, сумма, комментарий) и продолжает с ним, второй не создаётся. После проведения проводки перечитываются и сверяются (Дт 5010, Кт 6310 или 4010, сумма); не те проводки: статус `failed`, сообщение в группу, документ остаётся в 1С для человека.
- **1С не меняется и не удаляется.** Если запись, уже записанную в 1С, исправили или удалили в Кассе, в группу приходит предупреждение «исправьте/удалите документ ПКО №... в 1С вручную». Пока запись не записана, исправление и удаление учитываются на следующей попытке. Приходы, внесённые в репетиции, при включении `live` сами не записываются: нужные возвращают командой `onec-retry`.
- **Команды администратора:** `onec-check` (только чтение: отвечает ли 1С, принят ли логин, есть ли счета, статья, организация, касса и валюта из настроек), `onec-status [--limit N]`, `onec-retry --id N`, `onec-skip --id N`. Шаги включения: `docs/deploy-windows.md`, раздел 3.4.
- **Проверено** на поддельной 1С в тестах, на настоящей базе ещё нет.

## Telegram (Mini App)

Тот же сайт открывается внутри Telegram как Mini App. Браузерная версия от этого не зависит и работает полностью без Telegram (у людей в России он идёт через VPN). Код: `server/src/telegram.ts`, `web/src/telegram.ts`, `web/src/TelegramLink.tsx`.

- **Включается токеном бота.** В файле настроек сервера задайте `TELEGRAM_BOT_TOKEN=...` (токен от `@BotFather`) и перезапустите службу. Без него все ответы `/api/telegram/*` это `404 telegram_disabled`, и приложение работает как раньше. Токен секретный: он лежит только в файле настроек, читаемом службой и администраторами.
- **Вход.** Telegram при запуске передаёт данные запуска (`initData`) в адресе (`#tgWebAppData=...`). `POST /api/telegram/login` с телом `{ initData }` проверяет подпись по правилу Telegram (HMAC-SHA256 с ключом, выведенным из токена бота) и давность (не старше часа, не из будущего); подделанные или устаревшие данные получают `401`. Если Telegram-аккаунт привязан к логину, ответ тот же, что у входа по паролю, и cookie сессии; непривязанный аккаунт получает `403 telegram_not_linked` и ничего больше. Отозванный логин через Telegram не входит.
- **Привязка.** Человек входит в Mini App логином и паролем, на экране появляется строка «Привязать Telegram» (данные запуска есть только внутри Telegram). `POST /api/telegram/link` (нужна сессия) привязывает аккаунт к логину; один аккаунт Telegram к одному логину (`409 telegram_taken` иначе), у логина один аккаунт за раз (новая привязка заменяет прежнюю). `DELETE /api/telegram/link` отвязывает. `GET /api/me` отдаёт `telegramLinked`. Дальше Mini App входит сам.
- **Скрипт Telegram с чужого сайта не грузится совсем.** Приложению нужны только данные запуска из адреса и два сообщения Telegram («готово» и «на всю высоту»), они написаны прямо в `web/src/telegram.ts`.
- Вечерний итог и бот (#15, #18) этим билетом не сделаны.

## День кассы и сверка

Смен нет: кассир ничего не открывает и не закрывает, все вносят в одну общую книгу. **День кассы идёт с 03:00 до 03:00 по Москве**: кассиры работают до 24:00, иногда вносят до 01:00, и ночные записи принадлежат дню, который заканчивается; в 03:00 сутки переворачиваются сами (это полночь по UTC). Код: `server/src/cash-day.ts` (граница дня одним местом, для сервера и для SQL), `server/src/reconciliations.ts`, `migrations/0013_reconciliations.sql`, на экране `web/src/ReconcileBar.tsx` (админ) и `web/src/ReconciliationsList.tsx` (смотрящий).

- **Сверка кассы.** Раньше пересчёт наличных был частью закрытия смены, теперь это отдельное действие одного человека, админа (роль `admin`): кнопка «Сверить кассу» в режиме «Касса», во вкладке «Журнал», когда угодно, лучше вечером. Он пересчитывает наличные и вводит, сколько денег лежит в кассе по каждой валюте (ноль допустим), Касса записывает за ним разницу и приводит книгу к насчитанному: недостача уменьшает остаток, излишек увеличивает. Кассиры этой кнопки не видят, у владельца её тоже нет.
- `POST /api/reconciliations` (только админ), тело `{ id, counted: [{ currency, amountMinor }, ...] }`: `id` (uuid) делает клиент, по одной сумме на каждую валюту (RUB и USD), целые минимальные единицы. Для каждой валюты система берёт расчётный остаток (что книга говорит об остатке кассы сейчас: начальный остаток плюс все записи плюс разницы прошлых сверок), насчитанный и разницу (насчитанный минус расчётный: минус это недостача, плюс излишек); остатки на это время удерживаются, чтобы ни одна запись не втиснулась между двумя цифрами. Ответ `201` и `{ reconciliation: { id, madeAt, madeBy, currencies: [{ currency, calculatedMinor, actualMinor, differenceMinor }] }, balances }`. Тот же `id` с теми же суммами от того же админа отвечает `200` как в первый раз (потерянный ответ не считает кассу дважды), с другими суммами или от другого человека `409 reconciliation_id_conflict`. Кассир и смотрящий получают `403`. Сверку можно делать сколько угодно раз, каждая считается от книги в том виде, как её оставила прошлая. Сверка не меняется и не удаляется (база не даёт).
- `GET /api/reconciliations` (смотрящий и админ): сверки, новые первыми. Страницы: `limit` (до 100) и `before` (время последней сверки прошлой страницы), в ответе `nextBefore`.
- **В итогах** разница сверок за период в `differenceMinor`, и по-прежнему `открытие + приход - расход - передача + разница = закрытие`; разница относится к дню, в котором сделана сверка. На экране смотрящего вкладка «Сверки» (список: кто, когда, по книге, насчитано, разница) и строка «Разница при сверке» в «Итогах».
- **Что стало со старыми сменами.** Закрытые смены, в которых был пересчёт, миграцией `0013` перенесены в сверки (с тем же `id`, временем закрытия и тем, кто закрыл), поэтому остатки и итоги прошлого не изменились. Таблицы `shifts` и `shift_balances` и колонка `operations.shift_id` остались как история и больше нигде не читаются; новые записи в смену не попадают. Прежний средний курс смены тоже больше не используется: расходы без курса считаются по среднему курсу дня (см. «Курс и доллары»), поэтому доллары таких старых расходов могли чуть сдвинуться. Записи, внесённые между 00:00 и 03:00, переехали на предыдущий день кассы.
- **Телефоны, у которых в очереди остались записи со сменой.** Поле `shiftId` в `POST /api/operations` принимается и игнорируется: запись без связи не отклоняется из-за того, что смен больше нет. Адреса `/api/shifts*` убраны.
- **Что решено без вас и можно поменять.** Менять и удалять запись может только её автор, также и админ (если нужно, чтобы админ правил чужие, это одно условие в `server/src/ledger.ts`, `changeOperation`). О результате сверки в группу Telegram Касса не пишет.


## Правка, удаление и история

- `PUT /api/operations/:id` (кассир или админ, и только автор записи): правка. Тело как у нового внесения, без `id`, плюс необязательная `reason` (до 500 символов). Заменяет редактируемые поля целиком: сумма, валюта, категория, получатель, код клиента, комментарий; что не прислано, очищается. **Тип (приход или расход), автор и время записи не меняются.** Те же правила проверки, что при внесении. Если ничего не изменилось, ничего не записывается и версия не растёт. Параметры в строке запроса не принимаются (`400`), чтобы причина не терялась молча: она передаётся только в теле.
- `DELETE /api/operations/:id` (кассир или админ, и только автор записи), тело необязательное: `{ reason? }`; пустое тело допустимо и при `Content-Type: application/json`, а параметры в строке запроса дают `400`. Удаление логическое: запись скрывается, физически остаётся. Восстановления нет. Повторный запрос безвреден.
- Остаток может уйти в минус и при правке с удалением: правка и удаление записей не проверяют остаток. Правки идут в одной транзакции под блокировкой обеих валют, поэтому две правки одной записи не перемешиваются.
- Текст (комментарий, получатель, код клиента, причина) обрезается по краям; одиночная половина суррогатной пары заменяется на U+FFFD ещё до сравнения и сохранения, чтобы повтор того же запроса не считался изменением. Идентификатор операции в путях `/api/operations/:id...` должен быть uuid в обычной записи, иначе `400` (форма `urn:uuid:...` не принимается).
- Время изменения берётся, когда до запроса дошла очередь (после блокировки), поэтому в истории оно не идёт назад.
- Другие ответы: `403` чужая запись или смотрящий, `404` нет такой записи, `409 operation_deleted` запись уже удалена, `409 type_cannot_change` попытка сменить тип.
- Ответ на правку и удаление: `{ operation, balances }`. У операции есть `revision` (сколько раз её меняли, 0 значит как записана), `deletedAt` и `deletedBy`.
- `GET /api/operations/:id/history` (смотрящий и админ): как записана операция (`created`) и каждое изменение (`changes`: версия, `edit` или `delete`, время, автор, причина, значения `before` и `after`). Кассир истории не получает, даже своей.
- Журнал: параметр `deleted` (`exclude` по умолчанию, `include`, `only`) только для смотрящего, кассиру `403`. Удалённые записи не входят в остатки, подсказки кодов клиентов и валюту по умолчанию.
- Повтор исходного внесения (потерянный ответ, офлайн-очередь) после правки или удаления отвечает `200` с текущим состоянием: сравнивается исходное содержимое, а не текущее. Операция и остатки в таком ответе прочитаны из одного снимка базы, поэтому правка, прошедшая параллельно, не даёт ответа из двух разных моментов.
- Гарантии на уровне базы (миграция `0004_corrections.sql`), независимо от приложения: операции нельзя физически удалить (`DELETE`, `TRUNCATE` запрещены), строки истории нельзя менять и удалять, операция меняется только вместе со следующей версией и строкой истории (проверяется при завершении транзакции), причём строка должна говорить правду: что было до (все шесть полей), `edit` или `delete` соответствует изменению, а у удаления время и автор совпадают с `deleted_at` и `deleted_by`. Удалённая операция неизменна, новая всегда начинается с версии 0 и не удалённой. Функции проверок читают таблицы по полным именам с закреплённым `search_path`, поэтому временная таблица с тем же именем их не подменит. Чтобы всё же почистить данные перед запуском, разработчик отключает триггеры сознательно.
- Известный предел: ожидание блокировки валюты не ограничено по времени, и каждый ожидающий занимает одно из 10 соединений пула. Правки и удаления делают единицы людей, одна занимает десятки миллисекунд; всплеск в сотни одновременных правок мог бы занять пул, и часть запросов получила бы `500`. Для кассы это недостижимо, поэтому очередь и таймаут не добавлялись.
- `GET /api/client-codes?prefix=`: ранее вводившиеся коды клиентов, последние первыми, без учёта регистра, не больше восьми.
- `GET /api/operations/defaults`: валюта, которой этот кассир пользовался последней (по умолчанию RUB).

## Работа без связи

Кассир может вносить приход и расход без интернета. Код: `web/src/queue.ts` (очередь), `queue-store.ts` (хранение на телефоне, IndexedDB), `QueueBanner.tsx` и `EntryStatus.tsx` (что видит кассир), `web/sw/sw.js` (запуск без сети).

- **Запись сначала на телефон, потом на сервер.** Каждое внесение кассира сохраняется в IndexedDB и только затем отправляется. Если сервер ответил в течение 3 секунд, всё как обычно: «Записано». Если связи нет, сервер ответил ошибкой или не отвечает дольше 3 секунд, запись остаётся на телефоне, форма очищается, под ней написано «Сохранено на телефоне, на сервер не ушло: …» с причиной и тем, что будет дальше, а внизу появляется жёлтая плашка «Не отправлено: N». Когда запись дошла до сервера, надпись под формой сама меняется на «Записано». Закрытое приложение и перезагрузка телефона записи не теряют. Если телефон не принял запись (хранилище переполнено или закрыто), форма ничего не очищает и говорит об этом: запись тогда есть только в форме, и повторное нажатие отправит её с тем же `id`. Если кассир нажал кнопку во второй форме, пока первая запись ещё идёт, вторая не принимается (форма просит подождать секунду и нажать ещё раз): иначе она затёрла бы первую на телефоне. Если сессия кончилась, а телефон не смог сохранить запись, форма остаётся на экране и пишет, что делать.
- **Отправка идёт сама, пока приложение открыто**: при появлении связи (событие `online`), при открытии приложения и возврате на экран, по таймеру (через 3, 10, 30, 60 секунд после неудач, дальше раз в минуту) и по кнопке «Отправить сейчас». Закрытое приложение ничего не отправляет (фоновой отправки нет, в Safari на iPhone её не существует), плашка так и пишет.
- **По порядку.** Записи уходят по одной, старые первыми: новая не обгоняет те, что ждут на телефоне. Отправка останавливается на первой записи, до сервера с которой не достучались.
- **Ровно один раз.** У записи с самого начала есть `id`, и он не меняется. Сервер сохраняет `id` один раз и на повтор отвечает «уже сохранено» (`200`), поэтому потерянный ответ или повторная отправка не создают дубль (см. «Приход, расход и остатки»). Ответ считается «сервер записал», только если он про эту запись: страница входа в Wi-Fi или прокси, ответившие `200`, запись с телефона не удаляют. Запросы не висят вечно: на отправку 10 секунд, на остальное 15.
- **Только под логином автора.** Сервер берёт автора из сессии, поэтому запись уходит, только пока в приложении вошёл тот, кто её внёс (проверяется перед каждой отправкой). Вместе с записью идёт заголовок `X-Kassa-As` с логином автора, и сервер отвечает `409 wrong_session`, если сессия чужая (другая вкладка вошла другим кассиром, пока шла отправка): запись не окажется на другом кассире. Записи других кассиров на этом телефоне видны под плашкой, и если человек уже не работает, их можно удалить с подтверждением. Выход при неотправленных записях предупреждает.
- **Сессия кончилась**: записи остаются на телефоне, экран входа пишет, сколько их ждёт, после входа они уходят сами.
- **Сервер отказал по содержанию** (данные, которые он не может принять, или чужая запись): запись не пропадает и не отправляется без конца. Она остаётся в списке плашки с причиной, с кнопками «Отправить снова» и «Удалить с телефона» (удаление нужно подтвердить). Запись, которую только что ввели и которую сервер сразу отклонил, на телефоне не остаётся: форма показывает причину, и сумму можно поправить.
- **Приложение открывается без связи.** Service worker (`sw.js`, его версию и список файлов вписывает сборка Vite) кладёт копию приложения на телефон целиком, а не по частям (файл, оказавшийся страницей входа в Wi-Fi или ответом прокси вместо скрипта, копию не принимает), и новая версия вступает в силу, только когда скачана целиком. Страницу он берёт у сервера, а если тот не ответил за 5 секунд или ответил ошибкой `5xx` (приложение обновляется, прокси говорит `502`/`503`/`504`), открывает копию с телефона. Всё под `/api/` не кэшируется никогда: остатки, журнал и записи всегда спрашиваются у сервера. Телефон помнит последнего вошедшего кассира, список категорий расхода и валюту последней записи (`localStorage`), поэтому расход можно внести и без связи, а форма открывается в валюте последней записи, сделанной на этом телефоне (в том числе ещё не отправленной). Ответ сервера о валюте нужен, только если телефон ничего не помнит, и он никогда не меняет валюту, когда кассир уже что-то ввёл или выбрал. Приложение просит у браузера не очищать его хранилище (`navigator.storage.persist()`).
- **Без связи недоступно**: остатки (на экране «Нет связи», рядом число неотправленных записей), журнал, правка, удаление, история.
- **Несколько вкладок** одного браузера делят очередь (`BroadcastChannel`, замок `navigator.locks` на отправку).
- **Известные пределы.** Время записи на сервере это время её получения, а не ввода: запись, внесённая без связи в 10:02 и дошедшая в 10:40, в журнале стоит на 10:40 (время ввода на телефоне хранится в очереди и видно в плашке, но на сервер пока не передаётся). Неотправленную запись нельзя исправить: ошибку исправляют в «Журнале», когда запись дойдёт, или удаляют запись с телефона и вносят заново. Проверки на повтор по смыслу (та же сумма, тот же код клиента) нет: если кассир не заметил, что запись уже внесена, и внёс её ещё раз, это две записи. То, что кассир удалил запись с телефона, сервер не узнаёт. Если сервер сохранил запись, а ответ потерялся, надпись «на сервер не ушло» может быть неверна: запись уже в журнале, повторная отправка дубля не создаст, поэтому перед удалением записи с телефона и повторным внесением нужно смотреть журнал. Первый запуск после обновления приложения при плохой связи может показать пустой экран, если страница дошла, а новые файлы нет: достаточно открыть приложение ещё раз. Страница, открытая до обновления, работает на прежней версии, пока её не откроют заново. Если в браузере нет IndexedDB совсем, записи живут только в памяти открытой страницы и пропадут при закрытии: приложение это пока не показывает. Заголовок `X-Kassa-As` сервер пока не требует (его нет у старых страниц), поэтому проверка автора действует только для страниц новой версии. Надёжность хранилища на iPhone проверяется на настоящем телефоне, установленном «на экран Домой» (тикет #13). По документации Apple, для сайтов в Safari хранилище может быть очищено после недели без использования, для приложения на экране «Домой» это ограничение не действует (не проверено).

## Развёртывание на сервере

Сервер владельца работает под Windows 10: службы Windows без Docker (приложение, PostgreSQL 16, Caddy с автоматическим HTTPS). Подробная инструкция с командами, проверкой после установки, резервными копиями, обновлением, откатом и разбором проблем: [docs/deploy-windows.md](docs/deploy-windows.md).

Скрипты лежат в `deploy/windows/` (PowerShell 5.1, он есть в каждой Windows 10) и `deploy/` (Node.js):

- установка: `setup.ps1` (папки, база, настройки, первая сборка), `download-tools.ps1` (WinSW и Caddy с проверкой SHA-256), `install-services.ps1` (службы, их учётные записи, брандмауэр, HTTPS), `power.ps1` (сон, часы), `kassa.ps1` (команды администратора с настройками машины);
- работа: `update.ps1` (обновление и откат одной командой, с копией базы перед ним и возвратом при сбое), `verify.ps1` (проверка всей установки), `uninstall-services.ps1`, `build.ps1`;
- копии: `backup.ps1` и `deploy/backup.mjs` (сжатая копия, ротация: ночные 14, перед обновлением 5, `-Status`), `restore.ps1` и `deploy/restore.mjs` (`-Check`: проверка копии в пробной базе; `-Replace`: замена рабочей базы с сохранением прежней, обе замены имён одной транзакцией; без одного из двух ничего не делает), `schedule-backup.ps1` (ночное задание в Планировщике);
- проверки: `lint.ps1` (сами скрипты без Windows), `deploy/check.mjs` (работающий сервер по адресу), `deploy/setup-database.mjs` (роль, база в UTF8, файл настроек).

Файл настроек вне репозитория: образец `deploy/kassa.env.example`. `npm run admin -w server -- migrate` применяет миграции базы отдельно от запуска сервера; код выхода 3: база не такая, как нужно (не UTF8, изменена более новой версией), 4: миграция не применилась и ничего не изменилось (скрипт обновления возвращает прежнюю версию), 1: другая ошибка, возможно, часть миграций уже применена. Сервер отказывается работать на базе, которую изменила более новая версия (иначе остатки могли бы быть неверными; аварийный выход `ALLOW_NEWER_SCHEMA=1`), и на базе не в UTF8.

## Сборка и запуск как в проде

```sh
npm run build
DATABASE_URL=... npm start   # сервер отдаёт и API, и web/dist на одном адресе
```

На HTTPS задайте `NODE_ENV=production` (или `COOKIE_SECURE=true`), иначе cookie сессии не получит флаг `Secure`. По умолчанию сервер слушает только `127.0.0.1` (порт `3000`). Внутри контейнера или за прокси на другой машине задайте `HOST=0.0.0.0`, порт меняется через `PORT`. Маршруты приложения не должны содержать точку: запрос пути с расширением считается запросом файла и при его отсутствии получает честный `404`, а не оболочку.

## Тесты

Тесты ходят только в публичный HTTP API сервера и работают с настоящей PostgreSQL: подмен базы нет. Для каждого теста создаётся и потом удаляется отдельная база.

1. Нужна роль PostgreSQL-суперпользователь (как в CI): тесты создают и удаляют базы, а тесты `deploy/setup-database.mjs` ещё и роли. Адрес сервера задаётся переменной `TEST_DATABASE_URL`, по умолчанию `postgres://kassa_test:kassa_test@localhost:5432/postgres`. Создать такую роль можно так:

   ```sh
   psql -U postgres -c "CREATE ROLE kassa_test LOGIN SUPERUSER PASSWORD 'kassa_test'"
   ```

2. Запуск:

   ```sh
   npm test               # тесты сервера (HTTP API на настоящей базе) и веба (очередь внесения)
   npm run typecheck      # проверка типов сервера и веба
   npm run test:e2e       # сквозные тесты в настоящем браузере: собирает веб и гоняет работу без связи
   ```

   Для `test:e2e` нужен Chromium: `npx playwright install chromium` (или переменная `CHROMIUM_PATH` с путём к нему). Тестам копий базы (`server/test/backup-scripts.test.ts`) нужны `pg_dump` и `pg_restore` версии не ниже сервера (в Ubuntu пакет `postgresql-client-16`) в `PATH`. Тестам скриптов PowerShell (`server/test/powershell-scripts.test.ts`: «выдуманная машина» с настоящим git-репозиторием и заглушками служб и `icacls`) нужен `pwsh` (PowerShell 7) в `PATH`; без него эти тесты пропускаются. Они показывают, что решают скрипты, но не как ведёт себя Windows PowerShell 5.1 и сама Windows.

Если прогон оборвался посередине, могли остаться базы `kassa_test_...`: их можно удалить командой `DROP DATABASE`.

## CI

GitHub Actions (`.github/workflows/ci.yml`) на каждый push в любую ветку. Задание `check` (Ubuntu): проверка типов, тесты на PostgreSQL 16, сборка, проверка скриптов `deploy/windows` (`lint.ps1`), сквозные тесты в браузере (`npm run test:e2e`). Задание `windows` (`windows-latest`, Windows PowerShell 5.1): ставит PostgreSQL 16 установщиком, прогоняет `setup.ps1`, `download-tools.ps1`, `install-services.ps1`, ночное задание копий, `restore.ps1`, `update.ps1`, `verify.ps1`, `uninstall-services.ps1` и ждёт, что всё проходит. Перезагрузки оно проверить не может: это делается руками на настоящем сервере (инструкция, раздел 4.4). Когда задание писали, GitHub не запускал на этом репозитории ни одно задание (они заканчивались за три секунды без шагов), поэтому ни разу не видело, что у `windows` получится на самом деле.
